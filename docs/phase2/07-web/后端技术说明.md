# 后端技术说明（可直接纳入第二阶段报告）

## 1. 技术栈与运行环境

| 项 | 取值 |
| --- | --- |
| 语言/运行时 | Python 3.12.16（conda 环境 `DatabaseLab`） |
| Web 框架 | Flask 3.1.3、Jinja2（随 Flask） |
| 数据库驱动 | pyodbc 5.4.0 + ODBC Driver 18 for SQL Server |
| 测试 | pytest 9.2.0（`tests/`，31 项） |
| 数据库 | SQL Server 2025 17.0.1000.7，兼容级别 170；工作库 `TeabarDB_Phase2_Work`（v1.0），测试库 `TeabarDB_Phase2_Test` |
| 认证方式 | Windows 集成身份连接（本机实例仅 Windows 身份验证），业务身份用 `EXECUTE AS USER` 切换 |

依赖清单 `requirements.txt`，配置模板 `.env.example`（`TEABAR_DB_DRIVER/SERVER/NAME/TRUSTED/USER/PASSWORD/SECRET_KEY/SESSION_COOKIE_SECURE`）。连接串固定附加 `TrustServerCertificate=yes`，因为 ODBC 18 默认加密且本机证书为自签名。

## 2. 目录与分层

```text
Browser → Route/Controller → Service → DAO/Repository → teabar_api 视图与过程 → SQL Server
```

- **Route** 只做 HTTP 解析、模板渲染、状态码；HTML 页面与 `/api` 共用同一套 Service。
- **Service** 负责输入规范化（长度、数量范围、ID 格式、重复项）、角色复核、调用 DAO、把数据库错误翻译成 `AppError`。
- **DAO** 是唯一执行 SQL 的模块，全部 `?` 参数化；不拼接用户输入，不向浏览器暴露 SQL、路径或堆栈。
- **templates/static** 是组员 B 提供的可运行参考界面，字段契约已冻结（见给 C 的接口文档），C 可替换视觉层。

## 3. 连接与身份生命周期

`app/db.py`：

1. `Database.connect()` 用 pyodbc 建立连接，`autocommit=True`，连接串带 `Connection Timeout=5`。
2. `Database.connection()` 是上下文管理器，退出时关闭连接；所有正常/异常路径都不遗留连接或游标。
3. `Database.impersonate(conn, principal_name)` 只接受固定白名单 `web_guest_a/web_guest_b/web_member_a/web_member_b/web_clerk/web_manager`，执行 `EXECUTE AS USER = '<白名单值>'`，`finally` 中 `REVERT`。
4. `app/security.py::session_scope()` 每个请求：打开连接 → `usp_GetWebContext` 复核账号、会话版本、角色与绑定 → 与 Flask 会话中的 `principal_name/app_role/session_version` 比对 → 角色门禁 → 切换业务身份 → 交给 Service。任何复核失败清空会话并按未登录处理（401/跳转登录）。

购买者身份不通过参数传递：`teabar_auth.fn_CurrentIdentity()` 依据 `DATABASE_PRINCIPAL_ID()` 与 `PrincipalBinding` 解析出 `member_id/guest_id`，`vw_My*` 视图自动只返回本人数据。这避免了"客户端传 member_id"的越权面。

## 4. 参数化与 JSON 下单

- 所有普通查询/过程调用使用 qmark 占位符，例如 `SELECT ... FROM teabar_api.vw_Menu`、`EXEC teabar_api.usp_AdvanceOrder ?, ?`。
- 下单统一走 JSON 包装过程：

```sql
EXEC teabar_api.usp_PlacePaidOrderJson ?, ?, ?, ?, ?   -- order_id, items_json, specs_json, addons_json, payment_succeeded
```

`DAO` 将三个数组分别 `json.dumps` 绑定；应用先做订单号 1–10 位 ASCII、items 非空、数量 1–99、规格/加料去重等校验，数据库再用 OPENJSON 严格校验字段集合、类型、重复与引用。订单/明细号由 `secrets.token_hex` 生成（`O`/`I` + 9 位大写十六进制），若遇到主键冲突（2601/2627）整组重新生成，最多 3 次。

## 5. 事务边界

应用连接 `autocommit=True`，不自行开启长事务。下单、退款、状态推进、积分、补库的事务由数据库过程内的 `TRY/CATCH + XACT_ABORT` 保证：

- 库存不足、规格非法、零消耗等抛错时整单不产生订单/明细/扣库（测试 `test_stock_insufficient_rolls_back` 用订单计数与库存快照验证）；
- 退款按消耗快照返库并置 `已取消`，重复退款被过程拒绝（52106）；
- 首次 `已完成` 时按整单金额向下取整加积分，重复完成不重复加（状态机 52103/52104 拒绝）。

## 6. 统一错误与日志

`app/errors.py` 将接口约定的错误号映射为固定应用错误码，例如：

| SQL | 应用码 | HTTP | 场景 |
| --- | --- | --- | --- |
| 52000 | `purchase_identity` | 403 | 当前身份未绑定购买身份 |
| 52005/52007/52008/52009 | `product_unavailable`/`spec_invalid`/`spec_duplicate`/`spec_missing` | 409/400 | 商品与规格 |
| 52016 | `stock_insufficient` | 409 | 库存不足整单回滚 |
| 52018 | `zero_consumption` | 409 | 逐明细零消耗 |
| 52103/52105/52106 | `status_transition`/`refund_other`/`refund_state` | 409/403/409 | 状态与退款 |
| 52600–52604 | `json_invalid`/`json_shape`/`json_value`/`json_duplicate`/`json_reference` | 400 | JSON 参数 |
| 52700 | `session_invalid` | 401 | 会话/映射失效 |
| 2601/2627、547、229 | `duplicate_key`/`constraint_violation`/`permission_denied` | 409/409/403 | 唯一、约束、权限 |

未知异常统一 `internal_error` 500；连接/驱动错误 `database_error` 503。`logger.exception` 记录可定位原因，日志不写密码、连接串或完整敏感表单。响应中的 `error.message` 为面向用户的中文提示，不包含 SQL 文本、对象名或堆栈。

## 7. 安全实现

- CSRF：`before_request` 对所有 POST/PUT/PATCH/DELETE 校验表单 `csrf_token` 或 `X-CSRF-Token`，常量时间比较；GET 页面通过 `base.html` 注入 token。
- 会话：只存标识，不存密码或哈希；`HttpOnly`、`SameSite=Lax`；`SECRET_KEY` 来自环境变量，不提交真实值。
- 会话失效：`session_version` 在每次请求复核，管理员改版本/停用账号后旧会话立即 401（测试覆盖）。
- 授权：`session_scope(roles=...)` 在服务端强制角色；顾客调用店员/店长接口返回 403，HTML 页面重定向回首页；隐藏按钮之外的直接请求同样被拒。
- SQL 注入：全部参数化；唯一字符串拼接是白名单内的 `EXECUTE AS USER` 身份名常量，且先做集合校验。
- 浏览器不直连数据库；数据库账号密码不出现在模板或响应中。

## 8. 测试

- `test_auth.py`：登录页、错误密码、三种角色登录、退出、未登录 401/302、CSRF 缺失、会话版本失效后旧会话被拒。
