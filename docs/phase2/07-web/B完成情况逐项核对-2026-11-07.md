## 优先处理的问题

1. **连接池与异常清理**：全应用没有 `pyodbc.pooling = False`。`Database.impersonate()` 在进入 try/finally 前执行 EXECUTE AS，失败时游标缺少显式关闭；REVERT 失败被静默忽略。没有显式清理遗留事务再 REVERT，也缺异常路径、连接身份复用测试。违反 D03 和数据库接口通用规则。
2. **编号碰撞重试错误**：`normalize_payload()` 在循环外生成明细 ID；重试只生成订单 ID，明细主键碰撞会持续失败。任何 duplicate_key 都会重试，没有识别限定为订单/明细主键，也没有测试证明回滚后才重试。
3. **日志未落实**：仅有 basicConfig 和未知异常 logger.exception。业务 AppError 的 detail 未被处理器记录，没有请求 ID、用户、角色、操作、错误码、结果的完整日志；无法兑现最终“错误可定位”的验收。
4. **匿名菜单与原决策不符**：`/menu` 和 `/api/menu` 都要求登录；D03 明确未登录可看公开菜单，当前测试反而固定了匿名跳转行为。
5. **表单体验与重复提交**：HTML 下单只构造一条明细且强制 payment_succeeded=True；多商品与付款失败仅 API 有入口。下单失败返回 redirect 响应但覆盖成 4xx，输入未保留；新下单没有一次性请求令牌或幂等键，CSRF 本身不防重复下单。退款/完成有数据库状态拒绝，不能据此推定创建订单也幂等。
6. **分层差距**：Service 无独立身份/角色校验，授权在 Route 调用的 session_scope 中；healthz 和数据库身份切换在 DAO 外直接执行 SQL；DAO 查询/过程执行和结果读取重复，没有通用执行器、nextset 或返回码处理。
7. **权限证据不足**：目前文档明确使用 Windows db_owner 入口。受限入口权限、身份切换异常、用户直连越权与 Web 会话的组合没有实测闭环。不能仅用 demo_* SQL 回归代替 web_* 与真实入口验证。
8. **安全默认值**：缺失密钥时回退固定 `dev-only-insecure-key`，run.py 默认 debug=True。应明确开发配置并让演示/非开发启动拒绝不安全默认值。公开 healthz 返回数据库和登录身份，也应收窄。
9. **测试覆盖不完整**：31 项没有独立 SQL 注入、主键碰撞、多商品成功、连接失败模拟、547 映射、退款他人订单、直接修改积分/历史快照、异常资源释放等完整证据。库存不足用例只断言订单数量，未核对所有明细/快照/库存不变；退款用例未断言返库数量。
10. **C 联调尚未验收**：参考模板与字段文档已提供，但文档明确尚未合并 C 最终页面，不能把“可供联调”算成“联调完成”。

## 需要纠正的现有文档结论

- 登录名 `NVARCHAR` 的 DATALENGTH 6—100 字节，正好对应 3—50 个 ASCII 字符；订单号 2—20 字节，正好对应 1—10 个 ASCII 字符。因此“长度不一致”两条反馈依据不成立，不应要求 A 放宽为 20 个字符。非法字符校验和尾随空白语义应另行验证。
- `_`/`-` 被错误拒绝的字符类问题有历史反馈，但本轮未成功连库重现，暂保留为待 A 复核，不能借字节长度误读否定或证实字符类问题。
- 已知限制第 5 节仍建议清理工作库，结果 README 却记载后来已完成重置；应统一时间状态。本轮未验证当前工作库是否仍干净。
- 后端技术说明写“所有异常路径释放资源”“Service 角色复核”“冲突整组重生成”“日志保留可定位原因”，均超出当前代码保证，应修正或补实现。
- B 清单仍全部 `[ ]`；完成后应按真实证据更新，不能统一打勾。项目计划及总任务表也仍保留 B 未开始的状态描述。
