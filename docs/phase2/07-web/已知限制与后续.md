# 已知限制与后续

## 1. 组员 A 的 v1.0 约束缺陷（已反馈，待修）

`CK_WebAccount_LoginName` 使用：

```sql
datalength(login_name) BETWEEN 6 AND 100
AND NOT (login_name collate Latin1_General_100_BIN2 like N'%[^a-z0-9._-]%')
```

在 `Latin1_General_100_BIN2` 下，方括号末尾的 `-` 被当作范围符号，导致所有含 `_` 的登录名（以及部分含 `-` 的）被拒绝。B 的初始化脚本因此改用不含 `_`/`-` 的演示登录名。含 `_`/`-` 的合法登录名仍被数据库拒绝，属于 v1.0 遗留缺陷。复现、影响与修复建议见[给 A 的缺陷反馈](给A的缺陷反馈.md)。

## 2. 登录名长度文档与实现不一致

接口约定第 3.1 节写"3—50 位"，`CK_WebAccount_LoginName` 与 `usp_GetWebCredential` 使用 6—100 字节；应用层按 3—50 校验。演示账号均 ≥6 位，当前不影响；正式交付前需由 A 统一文档/约束/过程，或由 B 调整应用校验。

## 3. 本机实例仅 Windows 身份验证

`SERVERPROPERTY('IsIntegratedSecurityOnly') = 1`，无法创建 SQL 登录 `teabar_web`。当前实现：

- 应用以 Windows 集成身份（`DESKTOP-BY-JIMM\zoujy`，`db_owner`）连接；
- 每个请求通过 `EXECUTE AS USER web_*` 收窄到对应业务角色；
- `teabar_web_app` 角色、`VIEW DEFINITION` 与 `IMPERSONATE` 授予已按接口约定创建，但尚无真实受限登录使用它。

因此 B 清单中"真实受限登录 + pyodbc 参数绑定 + Web 会话"的验收只完成到 `EXECUTE AS` 层。报告需明确说明：若切换到混合认证实例，应创建 SQL 登录 `teabar_web`、加入 `teabar_web_app`，应用连接串改为 `UID/PWD`，其余代码无需改动（连接串与初始化脚本已留出入口）。

## 4. JSON 包装过程与文档的细节差异

接口约定第 2.1 节写 `@order_id` 接受 1—10 位 ASCII；`usp_PlacePaidOrderJson` 实现校验为 2—20 字节 ASCII（`[A-Za-z0-9_-]`）。应用层自行按 1—10 位校验并只生成 10 位编号（`O`/`I` + 9 位十六进制），所以正常路径不受影响；差异应记录为 A 的实现/文档待对齐项，不修改已部署过程。

## 5. 测试库与数据清理

- pytest 固定连接 `TeabarDB_Phase2_Test`，不写工作库；测试会创建订单，库存/积分在用例内恢复，但订单数据保留（便于重复运行时观察）。重置：删除测试库，从 v0.1 备份还原 → 重新迁移 → 重新初始化账号（步骤见[演示账号与初始化](演示账号与初始化.md)）。
- 工作库 `TeabarDB_Phase2_Work` 在 B 联调阶段曾被冒烟脚本写入少量订单；最终演示前建议重置为干净 v1.0 并重跑 184 项回归。重置方式：从 v0.1 备份还原到新副本名（不要覆盖冻结源），重新执行 `@CommitMigration=1` 的迁移，再运行 `regression.sql` 与 `init_web_accounts.py`。

## 6. 其他边界

- 本地 HTTP 演示默认关闭 `Secure` Cookie；正式部署需 HTTPS 并设 `SESSION_COOKIE_SECURE=1`，同时更换 `TEABAR_SECRET_KEY`。
- 无自助注册、找回密码或账号维护页面；账号/密码/版本由管理员脚本维护（符合接口约定"本轮不新增自助注册"）。
- HTML 模板是 B 的可运行参考实现，尚未与 C 的最终页面合并；字段契约已冻结，见[接口与模板约定（给 C）](接口与模板约定-给C.md)。
- 没有真实支付、短信、并发压测或浏览器端截图证据；证据以 pytest 输出、SQL 日志和 CLI 冒烟记录为主。
- 本机实例 `@@SERVERNAME` 为改名前的 `DESKTOP-TGBENFE`，与 `SERVERPROPERTY('MachineName')` 不一致，属环境历史问题，不影响连接（`SERVER=localhost`）。
