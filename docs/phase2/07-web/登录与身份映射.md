# 登录与身份映射

## 1. WebAccount 与哈希

`teabar_auth.WebAccount` 由 v1.0 迁移创建，应用只通过两个认证过程访问：

| 过程 | 输入 | 返回 |
| --- | --- | --- |
| `teabar_auth.usp_GetWebCredential` | `@login_name NVARCHAR(MAX)` | `account_id, password_hash, session_version`（启用且匹配时一行） |
| `teabar_auth.usp_GetWebContext` | `@account_id INT, @session_version INT` | `account_id, app_role, principal_sid, principal_name, session_version`；无效抛 52700 |

- 密码由管理员脚本用 `werkzeug.security.generate_password_hash`（PBKDF2-SHA256 加盐）写入，应用用 `check_password_hash` 校验，数据库不存明文、SQL 不做明文比较。
- 登录名在应用层先转小写并匹配 `^[a-z0-9._-]{3,50}$`；数据库侧要求 6–100 字节小写 ASCII（存在文档/约束不一致，见[给 A 的缺陷反馈](给A的缺陷反馈.md)）。演示账号均为 6 位以上小写字母。
- 未知账号执行一次固定虚拟哈希校验，对外统一返回"登录名或密码不正确"，避免账号枚举。
- 认证过程不建立会话、不改积分或业务数据；账号停用/密码重置由管理员脚本递增 `session_version` 完成。

## 2. Flask 会话

`set_session()` 先 `session.clear()` 再写入，防止会话固定。会话只保存：

```text
account_id, session_version, app_role, principal_name, login_name
```

不保存密码、哈希或连接信息。Cookie 设置 `HttpOnly`、`SameSite=Lax`；本地 HTTP 演示默认不要求 `Secure`，部署到 HTTPS 时用 `SESSION_COOKIE_SECURE=1` 打开。

## 3. 每请求复核

`session_scope()` 在每次请求执行：

1. 读取 Flask 会话；无会话 → 401（API）或跳转登录（HTML）。
2. 打开新数据库连接，调用 `usp_GetWebContext(account_id, session_version)`。
3. 若返回 52700（账号停用、版本变化、SID/角色/绑定不一致）→ 清会话并要求重新登录。
4. 比对返回的 `principal_name/app_role/session_version` 与会话记录，不一致同样失效。
5. 按路由要求的角色做门禁（`roles=("customer","member")` 等）。
6. `EXECUTE AS USER <principal_name>` 切换到业务身份，调用 Service/DAO，退出时 `REVERT` 并关闭连接。

因此"禁用账号""递增版本""改绑身份"都会让旧会话立即失效，测试 `test_bumped_session_version_rejects_old_session` 覆盖了版本变化场景。

## 4. 数据库角色与购买身份映射

| 登录名 | app_role | 数据库用户（WITHOUT LOGIN） | 数据库角色 | 购买身份 |
| --- | --- | --- | --- | --- |
| `guesta` | customer | `web_guest_a` | `teabar_customer` | 游客 `0D9AB0CB-4ABA-49E6-B46C-645EB5CAC9F6` |
| `guestb` | customer | `web_guest_b` | `teabar_customer` | 游客 `83F678A7-6C90-4BEF-BC46-74E733EA1D37` |
| `membera` | member | `web_member_a` | `teabar_member` | 会员 `M001` |
| `memberb` | member | `web_member_b` | `teabar_member` | 会员 `M002` |
| `clerk1` | clerk | `web_clerk` | `teabar_clerk` | 无（工作身份） |
| `manager1` | manager | `web_manager` | `teabar_manager` | 无（工作身份） |

`teabar_auth.PrincipalBinding` 把 `principal_sid` 绑定到 `member_id` 或 `guest_id`；`teabar_auth.fn_CurrentIdentity()` 用 `DATABASE_PRINCIPAL_ID()` 查绑定，`vw_My*` 视图据此只返回本人数据。应用层不向下单过程传 `member_id/guest_id`，也没有"选择身份"的接口，因此无法通过改参数查看他人订单。

## 5. 初始化脚本

`database/admin/init_web_accounts.py` 只做管理员初始化，幂等、可重复执行：

```powershell
python database\admin\init_web_accounts.py --database TeabarDB_Phase2_Work
python database\admin\init_web_accounts.py --database TeabarDB_Phase2_Test
```

脚本行为：

1. 校验连接账号为 `db_owner/sysadmin`，且库名在 `TeabarDB_Phase2_Work / TeabarDB_Phase2_Test` 白名单内（拒绝冻结库）；
2. 创建应用角色 `teabar_web_app`：两个认证过程的 `EXECUTE`、6 个 `web_*` 用户与 4 个业务角色的 `VIEW DEFINITION`、6 个 `web_*` 用户的 `IMPERSONATE`；
3. 创建 6 个 `WITHOUT LOGIN` 用户并各加入唯一业务角色，写入 4 条 `PrincipalBinding`；
4. 写入 6 条 `WebAccount`（哈希，不存明文），逐条调用 `usp_GetWebContext` 自检，并做一次 `EXECUTE AS web_guest_a`/`REVERT` 自检；
5. `--dry-run` 全程回滚；`--reset-passwords` 为已存在账号重置演示密码并递增 `session_version`。

## 6. 已知限制

本机 SQL Server 实例仅启用 Windows 身份验证（`IsIntegratedSecurityOnly=1`），无法创建 SQL 登录 `teabar_web`。当前演示连接使用 Windows 集成身份（`db_owner`），业务调用通过 `EXECUTE AS USER web_*` 收窄到对应业务角色；`teabar_web_app` 角色与授予已按设计创建，但未作为登录入口使用。真实"受限应用登录"验收需在混合认证实例上补做，报告需按 B 清单要求说明该限制。
