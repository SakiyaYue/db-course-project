## 2. 本地准备

仓库根目录运行，预计1分钟内完成：

```powershell
python database\migrations\v0.1-to-v1.0\build-scripts.py
pwsh -File database\regression\validate-scripts.ps1
```

生成器读取冻结 `db_creation.sql`、`constraint.sql`、`role.sql`、`view.sql` 和目标源文件，输出完整 migration/regression、旧用例提取和回滚核验。应修改主体/模块源后重建，直接编辑生成文件会在重建时丢失。

检查实际 migration.sql 的配置为 `ExpectedDatabase=TeabarDB_Phase2_Work`、`CommitMigration=0`、`InjectFailure=0`。默认演练仍会执行事务内DDL，须获得数据库执行授权。

## 3. 创建独立副本

1. 管理员打开 [work-copy.sql](../../../database/regression/work-copy.sql)，核对源名、工作名和服务端目录。默认读取实例的备份/数据目录，本次使用MSSQL实例Backup/DATA路径；目录须存在且服务身份可写。旧版本不能返回默认路径时手工填写绝对目录。远程实例使用服务器磁盘。
2. 保持 `Execute=0` 查看计划；确认工作名尚不存在、物理路径独立。模板只支持一数据文件一日志文件，其他布局直接拒绝。
3. 在授权范围内设 `Execute=1` 完整执行：随机后缀备份和文件名，COPY_ONLY + CHECKSUM备份、VERIFYONLY校验、MOVE还原新库。保留输出的 `.bak` 路径。
4. 记录源名、目标名、备份、逻辑/物理文件与日志，后续只连接工作库。不要执行根目录 db_creation.sql 重置副本，该文件固定删除/重建冻结同名库。

模板不覆盖已有库，不含 DROP DATABASE 或 RESTORE WITH REPLACE。备份会写文件和服务器备份历史，不重写源业务行；COPY_ONLY保留正常差异备份基准。VERIFYONLY不能代替成功还原和源状态预检。

## 4. 按顺序验证

每步用新窗口/连接完整执行。SSMS保存结果和消息；sqlcmd加 `-b`，让未捕获错误返回非零退出码。

| 顺序 | 操作 | 预期证据 |
| --- | --- | --- |
| 1 | 默认 `CommitMigration=0, InjectFailure=0`，运行migration | PRE_MIGRATION的16表哈希、目标核对、DRY_RUN_ROLLED_BACK_TO_V0.1 |
| 2 | 运行verify-rollback | 源对象16/74/19、旧核心定义和行数通过；哈希与第1步逐表相等 |
| 3 | 主体设 `CommitMigration=0, InjectFailure=1`，重新生成并运行migration | 预期错误 **52809**、失败回滚输出；sqlcmd应非零退出 |
| 4 | 再运行verify-rollback | 新表/过程/索引/版本标记不存在、旧定义恢复；原表哈希等于故障前值 |
| 5 | 无未解决失败时，主体设 `CommitMigration=1, InjectFailure=0`，重新生成，授权后执行 | COMMITTED_V1.0；随后完整regression预期184项全部通过 |

故障注入只在预检和DDL全部通过后触发。其他错误号不能当作故障回滚验收成功。步骤1—4均应回到干净v0.1；核验不符就停止提交，重新获取副本。

授权后的sqlcmd形式如下。按环境填写实例与证据文件名；Windows集成认证不在命令中保存密码。原基线实测使用localhost。

```powershell
sqlcmd -S localhost -E -No -C -d TeabarDB_Phase2_Work -b -f 65001 -i database\migrations\v0.1-to-v1.0\migration.sql -o results\phase2\migration\01-dry-run.txt
$LASTEXITCODE
sqlcmd -S localhost -E -No -C -d TeabarDB_Phase2_Work -b -f 65001 -i database\regression\verify-rollback.sql -o results\phase2\migration\02-verify-dry-run.txt
$LASTEXITCODE
```

示例只展示前两步，后续分别保存独立日志。`-No -C`沿用本机课程环境；真实应用连接的认证、证书和秘密管理由B/管理员单独配置。执行后恢复源开关默认0/0并重新生成，仓库内迁移文件保持默认回滚。

## 5. 事务、冲突与恢复

迁移在一个事务中取得独占应用锁，对原16表加表级写锁，记录行数与按主码排序的全行SHA-256。DDL、过程升级、授权、目标检查和版本标记均在事务内；TRY/CATCH出错时整体回滚并重新抛错。前后哈希验证本次原行一致，不能只凭行数证明内容未变。

历史缺正消耗、订单缺明细/金额不符、样例偏离、核心不是冻结版、约束禁用/不受信任或同名目标对象冲突，直接拒绝。不修补原行、不按现配方推测历史、不覆盖未知对象。先调查来源，决定恢复冻结副本还是另立有记录的数据修复任务。

| 情况 | 恢复操作 |
| --- | --- |
| 演练结束、注入失败、事务内错误 | 确认事务回滚；新连接执行verify-rollback，比较PRE_MIGRATION哈希；相符才重试 |
| 断线/重启 | 等待服务器恢复，新连接检查库状态和回滚结果，不能只看断线提示 |
| 工作库污染、恢复检查失败或已提交v1.0 | 保留失败日志和现库，从冻结源或迁移前备份还原到**另一个新工作名**，逐文件指定新路径，不对冻结库DROP/REPLACE |
| 备份/还原中途失败 | 保留错误和计划路径，检查是否RESTORING；调查后用新名、新路径重新规划，不自动删库或删文件 |

更换工作名时，同步修改work-copy的Work，以及migration-body、regression-body、生成器中回滚核验模板的ExpectedDatabase，重新生成并检查。已提交迁移不能靠重跑“降级”；本项目不提供就地逆向迁移，由备份还原获得干净v0.1。若新名或文件布局不适用当前模板，先调整并复核。
