### 1.2 判断规则

1. `X → Y` 表示在同一个合法关系状态中，X 相同则 Y 相同；不表示同一对象跨时间不能改名、改价或变更状态。
2. 候选码必须唯一且最小。PK 和 NOT NULL UNIQUE 提供直接证据；跨表约束或过程业务规则推导的候选码另作说明。不从样例推断“姓名唯一”“一个商品只有一种规格”等依赖。
3. 1NF 检查属性是否是该业务域中的单值；可空外键不代表多值。可空字段按 SQL 可选属性语义讨论，不把 NULL 当作经典关系理论中的普通相等值来推导依赖。
4. 2NF 检查非主属性是否依赖任一候选码的真子集；3NF 检查每条非平凡依赖是否由超码决定，或右端为主属性；BCNF 要求每个非平凡决定因素都是超码。
5. 下文列主要业务依赖及关键派生依赖，省略平凡依赖与可由其推导的增广依赖。跨表 SUM、跨行最小参与数、时间区间和权限规则单独分析，不能当成单表范式已经保证的约束。

“满足 BCNF”的结论以本文列出的业务规则为前提，并不表示表不存在其他完整性、权限或并发问题。主属性指至少属于一个候选码的属性。

## 3. 逐表分析

### 3.1 `SalesOrder`：正式订单

**一行含义：一次购买交易的订单编号、会员或游客归属、创建时间、成交总额和当前状态。**

关系属性：`(order_id, member_id, guest_id, order_time, total_amount, status)`。`guest_id` 来自约束安装阶段，不能只看基础建表脚本。

- 主码及全部候选码：`{order_id}`。同一会员、同一游客都可多次购买，时间精度为秒也不保证唯一；没有其他候选码依据。
- 主要函数依赖：`order_id → member_id, guest_id, order_time, total_amount, status`。依据为 `PK_SalesOrder` 及一订单一组归属和成交事实的规则。
- 范式：字段单值满足 1NF；唯一候选码为单属性，不存在部分依赖，满足 2NF；未发现非码决定非主属性的单表依赖，满足 3NF 和 BCNF。会员手机号不在本表，不能写出本表中的“会员编号 → 手机号”传递依赖。
- 更新异常：插入时缺明细、修改时总额与明细不一致、删除时丢失交易历史，分别是跨表参与约束、汇总一致性和生命周期问题。现有下单过程要求至少一条明细并在事务内写入、核对总额；业务角色无直接写表权限。订单不提供物理删除入口。
- 建议：保留。`total_amount = SUM(OrderItem.sub_amount)` 是跨表聚合冗余，需要受控写入及回归；它不能被普通单表 CHECK 或 BCNF 自动保证。

不能假设 `member_id → guest_id` 或反向依赖：二择一是可空属性的归属约束，不是两个真实身份之间的一一映射。

### 3.2 `OrderItem`：订单明细与派生小计

**一行含义：某笔订单中的一条确定规格、加料配置的商品购买行，保存数量和成交事实。**

关系属性：`(item_id, order_id, product_id, product_name_snapshot, quantity, base_price_snapshot, unit_price, sub_amount)`。

- 主码及全部候选码：`{item_id}`。`(order_id, product_id)` 不唯一：同单同商品可用不同规格或加料重复出现；增加数量也不能获得有业务依据的候选码。
- 主要函数依赖：`item_id → 其余属性`；派生依赖为 `(unit_price, quantity) → sub_amount`，依据为 `CAST(unit_price * quantity AS DECIMAL(10,2)) PERSISTED NOT NULL`。在当前精确十进制价格、正整数数量和可表示金额范围内，还可由 `(quantity, sub_amount)` 推得 `unit_price`；这不改变范式结论。
- 范式：1NF、2NF 成立；若把八个属性全部纳入关系，`(unit_price, quantity)` 不是超码，右端 `sub_amount` 是非主属性，因此不满足 3NF，也不满足 BCNF。不能因为它由数据库自动计算就否认这条函数依赖。
- 更新异常：若小计是普通可写列，修改单价或数量而未同步小计会导致更新异常；现有计算列使这一特定不一致不可直接写入。插入明细而缺规格/消耗、删除明细破坏订单汇总和历史，仍需过程、事务和权限控制。修改当前商品信息时更新历史快照反而会破坏成交事实。
- 建议：保留现有计算列作为可解释的派生冗余；把排除 `sub_amount` 的七属性投影作为基础事实模式分析，该投影在已知业务依赖下满足 BCNF。报告须同时列明这两个口径，不能声称包含计算列的完整关系满足 3NF。

`product_id` 不决定历史名称、基础价或成交单价。同一商品在不同订单发生改名、改价或配置变化后，快照可以不同。成交单价依赖本次基础价及相关规格、加料快照的跨表集合，不能简化成 `base_price_snapshot → unit_price`。

若仅用于理论展示，可将基础事实投影配合确定性计算重新生成小计，无需新增一张“单价、数量、小计”业务表。是否调整物理计算列由后续目标模式决定；本轮不改 DDL。

### 3.3 `ItemSpec`：明细规格快照

**一行含义：一条订单明细在某种规格类型下的唯一选择，以及成交时的名称和差价。**

关系属性：`(item_id, spec_type, spec_id, spec_name_snapshot, price_delta_snapshot)`。

- 主码：`(item_id, spec_type)`；另一候选码：`(item_id, spec_id)`。后者虽没有单独声明 UNIQUE，但可由 PK 和受信任的复合 FK 推导。
- 主要函数依赖：`(item_id, spec_type) → spec_id, spec_name_snapshot, price_delta_snapshot`；`spec_id → spec_type`。后一条由 `Specification.spec_id` 主码及 `(spec_id, spec_type)` 复合外键保证。
- 范式：满足 1NF；快照非主属性对两个候选码均无已知部分依赖，满足 2NF；`item_id`、`spec_id`、`spec_type` 都是主属性，`spec_id → spec_type` 的右端是主属性，因此满足 3NF。但 `spec_id` 本身不是超码，违反 BCNF。
- 更新异常：`spec_type` 在多条选择中重复；如果没有约束，可能把同一个 `spec_id` 错写为不同类型。现有复合 FK 拒绝类型错配，PK 拒绝同明细同类型重复。规格名称和差价是历史事实，不能为消除“重复”批量覆盖。插入必须有明细和规格；删除该选择可能导致订单缺某类必选规格，这是跨表完整性问题。
- 建议：保留 3NF 设计，以主码直接表达“一明细一类型至多一个选项”。不为达到 BCNF 而削弱该业务约束；显式登记可控的类型冗余。

候选码推导：

```text
{item_id, spec_id}
  ── spec_id → spec_type ──> {item_id, spec_id, spec_type}
  ── PK(item_id, spec_type) ──> 全部 ItemSpec 属性
```

`item_id` 单独不能区分糖度、温度、杯型；`spec_id` 单独不能区分不同明细，故该组合是最小超码。`spec_id` 也不决定 `spec_name_snapshot` 或 `price_delta_snapshot`：规格可改名，商品差价可不同且可随时间调整。

BCNF 分解讨论：令 `R1(spec_id, spec_type)`、`R2(item_id, spec_id, spec_name_snapshot, price_delta_snapshot)`。交集为 `spec_id`，且 `spec_id → R1`，故分解无损；R1 已有现成的 `Specification(spec_id, spec_type)` 投影可利用。但是投影依赖不能单独推出 `(item_id, spec_type) → spec_id`，会失去直接保证“一明细一类型”的能力。

反例：同一个明细在 R2 同时选择两个不同的糖度 `spec_id`，两表各自的码和 `spec_id → spec_type` 都可满足，连接结果仍会违反原规则。恢复该规则需要额外跨表校验。因此该分解不保持关键依赖，当前保留更便于声明式约束的 3NF 关系。

### 3.4 `ItemAddOn`：明细加料快照

**一行含义：一条明细成交时选择的一种加料及其名称、每杯价格快照。**

- 属性与码：`(item_id, addon_id, addon_name_snapshot, price_snapshot)`；全部候选码为 `{(item_id, addon_id)}`，也是主码。同种加料同明细只选一次，数量沿用明细杯数。
- 主要函数依赖：`(item_id, addon_id) → addon_name_snapshot, price_snapshot`。加料改名、改价后，不同成交明细可保留不同快照，故不能推断 `addon_id → 历史名称或价格`。
- 范式：字段单值；两个非主属性无已知部分依赖和传递依赖，决定因素为联合码，满足 1NF、2NF、3NF 和 BCNF。
- 更新异常：插入依赖已有明细和加料是合理引用；修改当前加料不应更新快照；删除选择会影响成交价的解释，需禁止交易历史任意修改。这些不构成需要再拆表的规范化异常。
- 建议：保留现有历史关联表，继续由下单事务写入、权限保护。

### 3.5 `OrderItemIngredient`：明细原料消耗快照

**一行含义：一条明细的全部杯数在成交时消耗的某种原料总量，已经合并配方与加料来源。**

- 属性与码：`(item_id, ingredient_id, amount)`；全部候选码和主码为 `{(item_id, ingredient_id)}`。
- 主要函数依赖：`(item_id, ingredient_id) → amount`。同一原料在不同明细的用量不同；同一明细可消耗多种原料，不能减少决定因素。
- 范式：单值、无非主属性对码真子集的依赖、无非码决定非主属性，满足 BCNF。
- 更新异常：不存在应消除的配方主数据重复。插入量须大于零；修改当前配方不得重算已成交快照；删除快照会丢失退款返库依据。`amount > 0` 只能约束已有行，不能保证每条明细至少存在一行。
- 建议：保留，按 D01 在核心下单过程中补逐明细正消耗检查及“同单一条正常、一条零消耗”的整单失败反例。现有整单需求非空检查不能替代它。

### 3.6 `Product`：商品主数据

**一行含义：一种商品的当前名称、基础价格、上下架状态和描述。**

- 属性与码：`(product_id, product_name, base_price, status, description)`；全部候选码和主码为 `{product_id}`。名称未声明唯一，不是候选码。
- 主要函数依赖：`product_id → product_name, base_price, status, description`；无依据支持“名称决定价格”“状态决定价格”等依赖。
- 范式：单值；单属性候选码无部分依赖，未发现非主属性传递依赖，满足 BCNF。
- 更新异常：商品可先以下架状态建立，配置和订单各自独立存在，避免必须先有订单才能录入商品；改当前价格无需修改历史明细；有历史引用时删除受 FK 限制，下架替代物理删除。
- 建议：保留。商品改名或调价属于当前事实变化，历史快照保持原值。

### 3.7 `ProductSpecification`：商品规格配置

**一行含义：一种商品对一个规格选项的当前支持状态及每杯价格差。**

- 属性与码：`(product_id, spec_id, price_delta, status)`；全部候选码和主码为 `{(product_id, spec_id)}`。
- 主要函数依赖：`(product_id, spec_id) → price_delta, status`。不同商品的同一规格可差价不同，同商品不同规格也可状态不同。
- 范式：单值；两个非主属性依赖整个联合码，无已知传递依赖，满足 BCNF。`spec_type` 不在本表，不能将其他表的该属性误记为本表部分依赖。
- 更新异常：配置可在没有订单时录入；改配置只影响后续成交；删除被系数规则引用的配置受 FK 限制，已有历史订单也不能据此重写。规格完整选择由下单过程检查。
- 建议：保留，使用停用管理配置生命周期。允许负差价，最终成交价非负另由过程检查。

### 3.8 `Recipe`：基础配方

**一行含义：一种商品每杯基础配方中一种原料的用量。**

- 属性与码：`(product_id, ingredient_id, base_amount)`；全部候选码和主码为 `{(product_id, ingredient_id)}`。
- 主要函数依赖：`(product_id, ingredient_id) → base_amount`。同原料在不同商品中用量不同，同商品可含多原料。
- 范式：单值；用量完整依赖联合码，无其他非平凡决定因素，满足 BCNF。
- 更新异常：可在无订单时配置配方；修改配方不更新历史消耗；删除被规格系数引用的配方受复合 FK 限制。删除最后一条配方导致商品不能下单，是配置完整性问题，受控维护路径还需保持一致。
- 建议：保留当前二元关联。不能将多个原料编号或用量拼成商品表中的一个列表字段。

### 3.9 `SpecificationIngredient`：商品规格原料系数

**一行含义：某商品选择某规格选项时，对其基础配方中某原料的用量系数。**

- 属性与码：`(product_id, spec_id, ingredient_id, factor)`；全部候选码和主码为 `{(product_id, spec_id, ingredient_id)}`。
- 主要函数依赖：`(product_id, spec_id, ingredient_id) → factor`。不存在“某杯型对所有商品、所有原料都用同一系数”的规则，不能据样例删去决定因素。
- 范式：单值；`factor` 依赖完整三元码，无已知非码决定因素，满足 BCNF。
- 更新异常：配置引用须同时满足商品规格、商品配方；改变系数只影响未来消耗；删除显式系数行会回到过程默认系数 1，并不是“消耗为零”。历史订单仍依赖旧消耗快照。
- 建议：保留三元结构。系数 0 合法，但最终每条明细是否有正消耗应由 D01 独立核对；计件用量整数规则由受控过程检查。

### 3.10 `Ingredient`：原料与当前库存

**一行含义：单门店的一种原料、统一计量单位、当前库存和人工维护的可用状态。**

- 属性与码：`(ingredient_id, ingredient_name, unit, stock, status)`；全部候选码和主码为 `{ingredient_id}`。原料名称未声明唯一。
- 主要函数依赖：`ingredient_id → ingredient_name, unit, stock, status`。单位不决定库存；库存也不决定状态，当前 CHECK 没有强制“零库存等于缺货”。
- 范式：各属性单值；无部分依赖及已知非码传递依赖，满足 BCNF。单门店只有一份当前库存，没有 `store_id` 或仓库维度导致的多值事实。
- 更新异常：原料可先建档再补库；库存并发覆盖是事务问题，不是拆表就能解决；被配方或历史引用时删除受 FK 限制，不能导致历史用量失去解释。
- 建议：保留单门店库存状态。已引用或非零库存原料的单位变更由 `usp_SaveIngredient` 拒绝；若未来增加多仓或库存流水，应按新需求重新建模。

### 3.11 `Member`：会员资料与当前积分

**一行含义：一名会员的当前姓名、唯一联系手机号和积分余额。**

- 属性与码：`(member_id, name, phone, points)`；主码为 `member_id`；全部候选码为 `{member_id}`、`{phone}`，手机号 NOT NULL UNIQUE。
- 主要函数依赖：`member_id → name, phone, points`；`phone → member_id, name, points`。这来自项目手机号唯一规则，不是样例巧合。
- 范式：单值；两个候选码都是单属性，无部分依赖；两个非平凡决定因素都是候选码，满足 BCNF。`member_id → phone → name` 经过另一个候选码，不构成违反 3NF 的非码传递依赖。
- 更新异常：可无订单先登记会员；更正手机号只改主档，不复制到订单；有订单或身份绑定引用时删除受 FK 限制。积分重复结算是状态流转和事务幂等问题。
- 建议：保留；积分由首次完成订单过程增加，资料维护过程不接受任意积分写入。手机号可变并不使它在当前关系状态中失去候选码资格。

### 3.12 `Employee`：员工资料

**一行含义：一名员工的当前姓名、在职状态、月薪和业务岗位。**

- 属性与码：`(employee_id, name, status, salary, role)`；全部候选码和主码为 `{employee_id}`，员工姓名不唯一。
- 主要函数依赖：`employee_id → name, status, salary, role`。项目没有按岗位统一工资的规则，故 `role → salary` 不成立。
- 范式：属性单值；单属性码无部分依赖，无非码传递依赖，满足 BCNF。
- 更新异常：员工可在未排班时入职建档；薪资、岗位各保存一次；有排班时删除受 FK 限制，离职通过状态维护。更改岗位不会自动更改数据库角色，这属于授权管理边界。
- 建议：保留。数据库 principal 和角色成员关系不由姓名、员工岗位推导；本轮没有增加员工与 Web 账号的隐含一一对应。

### 3.13 `DutyRoster`：单人值班区间

**一行含义：一名员工在 `[start_time, end_time)` 内的一段值班，区间非空，同员工不同区间不重叠。**

- 属性与显式码：`(duty_id, employee_id, start_time, end_time)`；主码 `duty_id`，另有 NOT NULL UNIQUE `(employee_id, start_time)`。
- 主要函数依赖：`duty_id → employee_id, start_time, end_time`；`(employee_id, start_time) → duty_id, end_time`。业务过程禁止同员工非空区间重叠，还可推出 `(employee_id, end_time) → duty_id, start_time`。
- 范式：单值；在声明式约束口径下两个候选码、在合法非重叠业务状态下三个候选码均无非主属性部分依赖；已知决定因素均为候选码，满足 BCNF。
- 更新异常：员工独立建档后可添加排班；改员工姓名无需批量改排班；删除排班不丢失员工主档，但会改变按时间查询的历史值班团队。重叠排班是跨行区间约束问题，普通 UNIQUE 不能完整防止。
- 建议：保留并使用 `usp_SaveDutyRoster` 维护；该过程先锁定员工，再检查区间重叠，使同一员工维护串行化。不同员工同时值班允许，不能据此写出“订单时间 → 唯一员工”。

补充候选码的边界：同一员工若有两个不同开始时间、相同结束时间的非空区间，两个区间必重叠；故业务规则蕴含结束时间组合唯一。仅按 SQL PK/UK 检查，特权直接写表仍可能插入这种状态，所以该候选码须注明依赖过程规则，不能声称已存在对应 UNIQUE。

### 3.14 `Specification`：规格选项主数据

**一行含义：糖度、温度或杯型中的一个当前规格选项。**

- 属性与码：`(spec_id, spec_type, spec_name)`；主码为 `spec_id`；全部候选码为 `{spec_id}`、`{(spec_type, spec_name)}`。
- 主要函数依赖：`spec_id → spec_type, spec_name`；`(spec_type, spec_name) → spec_id`。`spec_name` 单独没有唯一约束，不是候选码。
- 范式：字段单值；两个属性组成的候选码没有真子集决定非主属性的已知依赖；主要决定因素均为候选码，满足 BCNF。
- 更新异常：选项可独立于商品配置和订单录入；改当前名称不改历史规格名；被配置或历史选择引用时删除受 FK 限制。类型修改可能破坏历史“一类型一选择”语义，现有过程禁止已使用规格更换类型。
- 建议：保留。`UNIQUE(spec_id, spec_type)` 包含已是候选码的 `spec_id`，仅为复合外键引用服务，不是第三个候选码，也不改变本表范式。

### 3.15 `AddOn`：加料主数据

**一行含义：一种加料当前的唯一名称、每杯价格、对应原料、每份用量和状态。**

- 属性与码：`(addon_id, addon_name, price, ingredient_id, extra_amount, status)`；主码 `addon_id`；全部候选码为 `{addon_id}`、`{addon_name}`。
- 主要函数依赖：两个候选码各自决定全部属性。当前“一种加料对应一种原料”不等于“一种原料只能用于一种加料”；`ingredient_id` 不决定加料名称、价格或用量。
- 范式：单值；两个单属性码无部分依赖，已知决定因素均为候选码，满足 BCNF。
- 更新异常：可在无成交记录时定义加料；原料单位只保存在原料表，不在加料表复制；改加料价不改历史选择，删除受历史 FK 限制。
- 建议：保留当前“一加料一原料”的业务简化。只有未来要求一加料由多种原料组成时，才需要增加加料配方关联。

### 3.16 `teabar_auth.PrincipalBinding`：购买身份绑定

**一行含义：一个数据库 principal 的 SID、名称与一个会员或游客购买身份之间的管理员维护绑定及启用状态。**

- 属性与码：`(principal_sid, principal_name, member_id, guest_id, is_active)`；主码 `principal_sid`；全部候选码为 `{principal_sid}`、`{principal_name}`。
- 主要函数依赖：两个候选码各自决定全部属性。`member_id`、`guest_id` 没有 UNIQUE，不能反推唯一 SID；“一个绑定仅选一种身份”不等于“一个身份仅能有一个绑定”。
- 范式：单值；两个单属性候选码无部分依赖，已知决定因素均为候选码，满足 BCNF。
- 更新异常：插入和维护需确保 SID、名称对应实际数据库主体，但表本身没有到系统目录的 FK；重命名或重建用户后可能发生绑定过期，必须管理员同步检查。删除或停用绑定会影响授权，不应删除既有订单历史。这些是安全对象生命周期问题。
- 建议：保留现有 SID 过滤机制，不擅自增加 `member_id` 唯一约束。D03 的 WebAccount 和 `web_*` 用户属于后续新增设计，本轮未对不存在的字段和约束作范式验收。

## 4. 更新异常的分类与处理

| 类别 | 项目实例 | 处理方式 | 是否要求拆表 |
| --- | --- | --- | --- |
| 同一当前事实重复保存 | 假如把会员手机号复制进每笔订单、把原料单位复制进每行配方 | 通过现有主档 FK 引用；本项目未这样重复建模 | 当前没有该拆分需求 |
| 派生事实重复保存 | `OrderItem.sub_amount` | 数据库计算列；完整关系范式例外须明确 | 不必新增金额乘法表 |
| 类型冗余 | `ItemSpec.spec_id → spec_type` | 复合 FK + 主码；保留 3NF 并解释 BCNF 取舍 | 已讨论分解，关键依赖不保持 |
| 跨表汇总与状态 | 订单金额、库存、会员积分 | 受控过程、事务、角色边界及回归 | 拆表不能自动保证一致性 |
| 历史快照与当前主档不同 | 改名、改价、改配方后历史保持原值 | 保护成交时事实；不反向同步历史 | 不应当作错误冗余删除 |

逐表插入、修改和删除影响已在第 3 节记录。父记录必须存在、历史记录不能随意删除、配置未完成不能销售等业务限制，不应为了凑“异常”而一律归因于未满足 3NF。

## 5. 对 v1.0 的输入结论

1. 现有分析没有给出强制拆分、合并业务表的理由。保留方向与 D02 一致，但最终目标模式及 DDL 仍需另行编制。
2. `OrderItem` 的计算小计明确登记为派生冗余；`ItemSpec` 明确登记为 3NF、非 BCNF，并保留“一明细一类型”的直接约束。
3. 函数依赖分析不能替代 D01 修复：新增逐明细正消耗检查、迁移源冲突预检及混合明细反例。
4. 目标模式需要设计 `WebAccount`、身份与授权对象、JSON 包装及错误码，不能仅用本轮现有表分析宣告新对象完成。
5. 下一步依据本文、[冗余说明](有意冗余与业务状态说明.md) 和 D01—D05 编制对象变更对照、目标数据字典及 ER；之后再准备迁移与回归。
