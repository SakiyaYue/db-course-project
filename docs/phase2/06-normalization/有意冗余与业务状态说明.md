# 有意冗余、历史快照与业务状态说明

日期：2026-11-06。负责人：组员 A。依据：[role.sql](../../../role.sql)、[db_creation.sql](../../../db_creation.sql)、[共同决策 D01—D05](../../../PHASE2-DECISIONS.md)。本轮为静态分析，未执行 SQL。

## 1. 商品名称、基础价格和成交单价

`Product.product_name`、`Product.base_price` 表示当前商品定义；`OrderItem.product_name_snapshot`、`base_price_snapshot` 表示该次成交使用的名称和基础价。两者随时间可以不同，不能将历史快照替换成连接当前主档的结果。

`usp_PlacePaidOrder` 从锁定的商品、商品规格配置和加料定义中取值，在数据库计算：

```text
unit_price
  = base_price_snapshot
  + 本明细所选规格的 price_delta_snapshot 合计
  + 本明细所选加料的 price_snapshot 合计
```

这是涉及相关子表集合的计价规则，不是 `product_id → unit_price` 或 `base_price_snapshot → unit_price`。规格差价可为负，最终成交单价须非负；客户端不能直接指定成交价格。

现有 `OrderItem.sub_amount` 是数据库持久化计算列：

```sql
CAST(unit_price * quantity AS DECIMAL(10, 2)) PERSISTED NOT NULL
```

它不能作为普通列单独插入、修改。保留该列可统一查询中的金额表达，但在关系范式分析中仍需承认 `(unit_price, quantity) → sub_amount` 带来的 3NF 例外，详见 [函数依赖分析 3.2](函数依赖与范式分析.md#32-orderitem订单明细与派生小计)。金额超出字段范围应报错，不能靠静默截断继续交易。

## 2. 规格名称、规格差价与加料快照

| 成交字段 | 当前来源 | 历史保留理由 |
| --- | --- | --- |
| `ItemSpec.spec_name_snapshot` | `Specification.spec_name` | 规格改名后仍可解释旧订单 |
| `ItemSpec.price_delta_snapshot` | `ProductSpecification.price_delta` | 同规格可因商品或成交时间不同而有不同差价 |
| `ItemAddOn.addon_name_snapshot` | `AddOn.addon_name` | 加料改名不改旧订单 |
| `ItemAddOn.price_snapshot` | `AddOn.price` | 加料调价不重算已成交价格 |

下单过程在同一事务内写入明细及相关快照，业务角色没有直接更新快照的权限。当前主档变更只影响未来订单。

`ItemSpec.spec_type` 需要另行说明：它与 `spec_id` 存在稳定的类型依赖，并非可随成交时间任意变化的名称快照。保留它是为了用主码直接限制“一明细一类型至多一项”，再以复合外键检查类型正确；这是满足 3NF、未满足 BCNF 的已解释冗余。

## 3. 原料消耗快照与退款

`OrderItemIngredient.amount` 保存该明细全部杯数在付款下单时实际扣减的原料量，不是每杯用量，也不是当前基础配方用量。

现有过程先计算基础配方用量与所选糖度、温度、杯型系数的乘积，未配置系数按 1 处理；再加上加料用量，乘以杯数，按 `(item_id, ingredient_id)` 汇总并保留两位小数，只写入正数快照。计件原料还须满足每杯用量为整数的规则。

`usp_RefundOrder` 只接受排队中订单，按其消耗快照逐原料汇总返库，再将状态改为已取消；不会读取新配方重算。重复退款因状态检查被拒绝。

例：某明细成交时扣减糖浆 20 ml，之后店长把当前配方调整为 25 ml。合法退款仍返还 20 ml。删除快照或用新配方覆盖快照都会失去这一依据。

D01 要求每条正式明细至少有一条正消耗。当前过程只检查整单需求非空，单表 `CHECK(amount > 0)` 也无法保证子行存在，因此此缺口仍待迁移阶段修复。历史不合规明细应由迁移预检列出并阻止迁移，不得按当前配方伪造历史消耗。

## 4. 订单总额与明细小计

`SalesOrder.total_amount` 保留整笔交易的成交金额，是相对于明细小计汇总的冗余值。

维护路径为：数据库计算每条成交单价 → 汇总 `CAST(unit_price * quantity AS DECIMAL(10,2))` → 同事务写入订单和明细 → 对照明细计算列合计，不一致抛出错误 `52017` 并走回滚路径。业务角色不能绕过过程直接更新订单金额或交易明细。

验收需分别核对：

1. 每条明细 `sub_amount` 与单价乘杯数一致。
2. 每笔订单 `total_amount` 与该订单明细小计合计一致，并单独识别没有明细的订单。
3. 当前商品、规格或加料改价后，历史金额和快照保持不变。
4. 下单失败时订单、明细、快照及库存均无部分变化。

金额汇总不属于普通单表函数依赖，订单表达到 BCNF 也不能自动保证它。取消订单保留原成交金额和明细，营收查询按业务状态决定是否纳入统计。

## 5. 原料库存与会员积分

### 5.1 `Ingredient.stock`

`stock` 是单门店当前可用数量。业务路径包括下单扣库、合法退款按快照返库、店长补库与盘点；库存不能简单等于“初始样例库存减全部历史消耗”。盘点、补库和已退款订单必须纳入解释。

下单按原料汇总需求、使用更新锁及保持锁扣减；库存不足或状态不允许时抛错并进入事务回滚。CHECK 保证库存非负，计件库存另有整数规则。补库与盘点由店长过程维护，店长也无直接更新库存权限。

`status` 是独立维护的可用/缺货状态，当前模型未规定由 `stock` 唯一计算得出。原料已被引用或有非零库存时，更改单位由保存过程拒绝；这对解释历史消耗量至关重要。

### 5.2 `Member.points`

`points` 是当前积分余额。现有状态推进过程只允许按“排队中 → 制作中 → 待取餐 → 已完成”流转；首次进入已完成时，会员积分增加 `FLOOR(total_amount)`。锁定订单及状态检查用于阻止重复完成重复加分。

积分不能在未核对初始余额及维护历史的情况下，直接当成当前订单全集重新 SUM 的结果。现有会员资料维护过程不允许任意修改积分，会员本人无直接修改权限。退款只适用于排队订单，因此当前退款流程不会冲销已经完成订单的积分。

库存和积分都是受事务维护的业务状态；把它们拆成另一张一对一表，并不能自动解决并发覆盖、重复结算或回滚问题。

## 6. 员工岗位与数据库角色

`Employee.role` 是业务岗位，当前只允许店员、店长；SQL Server 的 `teabar_customer`、`teabar_member`、`teabar_clerk`、`teabar_manager` 是数据库权限集合。它们属于不同事实，不能因为名称相似就视为规范化时需要合并的重复字段。

`usp_SaveEmployee` 只维护员工业务资料，不修改数据库角色成员关系。离职、岗位变化与账号禁用、授权变更需要管理流程明确同步，不能声称改 `Employee.status` 就已自动撤销数据库访问。

D03 已确定 Web 账号映射独立数据库用户的方向；WebAccount 的实际约束、安全对象和账号维护接口仍需在目标模式中设计。现有表也没有证明员工与 Web 账号一一对应。

## 7. 保留原则与后续验收

| 内容 | 当前处理建议 | 后续验证 |
| --- | --- | --- |
| 历史名称、价格、消耗快照 | 保留成交事实，禁止随主档同步重写 | 改名、改价、改配方后旧订单不变；退款按旧快照 |
| 小计、订单总额 | 保留计算列及受控汇总，明确关系范式例外和跨表约束 | 逐行乘法、逐单合计、失败无部分写入 |
| 规格类型冗余 | 保留 3NF 设计和复合 FK | 拒绝类型错配及同明细同类型重复选择 |
| 库存和积分状态 | 保留单门店当前余额，由受控事务维护 | 库存不足回滚、首次完成加分、重复操作拒绝 |
| 岗位与权限身份 | 分开建模，管理员负责授权和账号生命周期 | 角色边界、账号停用、本人数据隔离 |

以上是设计分析与验收要求。迁移脚本、JSON 包装、Web 认证和新增回归用例尚未实现，本文不将它们标为已通过。
