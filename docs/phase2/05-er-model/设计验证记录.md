# v0.1 ER 设计说明与场景验证记录

## 1. 图和表示法

- 清晰导出图：[根目录 ER 图修订版](../../../ER图_修订版.png)。
- 可编辑源：[Mermaid 源](../../../design/er/v0.1/ER图_v0.1.mmd)。
- 实线：数据库外键联系。
- 虚线：值班时间匹配或身份核对等非外键业务联系。
- `0..1`、`1..1`、`0..N`、`1..N` 表示最小/最大基数。
- `PK` 为主码，`UK` 为其他候选码或唯一组合，`FK` 为外码；`?` 表示可空。

图中 `SalesOrder — OrderItem` 和 `OrderItem — OrderItemIngredient` 使用业务要求的 `1..N`。关系表结构本身只能实现父端 `0..N`；前者由下单过程实现，后者仍有逐明细校验缺口。这一差异必须与图一起说明。

## 2. 场景一：多商品订单

### 输入场景

一笔订单同时购买两种商品；其中同一种商品也允许因规格不同出现在两条明细中。

### ER 表达

```text
SalesOrder 1
  └─ OrderItem 1..N
       ├─ Product 1
       ├─ ItemSpec 0..3
       ├─ ItemAddOn 0..N
       └─ OrderItemIngredient 1..N（业务要求）
```

### 核对结论

- `OrderItem.item_id` 独立标识明细，没有 `(order_id, product_id)` 唯一约束，因此不会错误限制同一商品只能出现一次。
- 每条明细保存自己的数量、成交价、规格和加料快照。
- `SalesOrder.total_amount` 由全部明细小计汇总，回归视图检查一致性。
- 场景可以表达；逐明细快照下限仍待补强。

## 3. 场景二：会员购买

### 输入场景

绑定会员 M001 的可信购买身份创建订单。

### 数据路径

```text
database principal SID
→ PrincipalBinding.member_id
→ usp_PlacePaidOrder
→ SalesOrder.member_id = M001, guest_id = NULL
→ vw_MyOrders / 退款过程按当前身份过滤
```

### 核对结论

- `Member — SalesOrder` 为会员端 `0..N`、订单端 `0..1`。
- 订单归属 CHECK 保证会员和游客不同时为空、也不同时存在。
- 数据库内部演示可验证本人范围；真实 Web 登录和 principal 映射尚未设计。

## 4. 场景三：游客购买

### 输入场景

没有会员档案的游客在同一会话中创建一笔或多笔订单。

### 数据路径

```text
database principal SID
→ PrincipalBinding.guest_id
→ usp_PlacePaidOrder
→ SalesOrder.guest_id = 会话UUID, member_id = NULL
```

### 核对结论

- 不需要为了游客订单保存姓名或手机号，因此 v0.1 没有 Guest 业务表。
- `guest_id` 不唯一，允许同一会话对应多笔订单。
- 旧样例的随机占位 UUID 不能反推出真实历史会话，也不能作为认证证据。
- 场景在数据库演示层可以表达；Web 会话生命周期待应用设计。

## 5. 场景四：规格和加料选择

### 输入场景

商品 P001 选择糖度、温度、杯型，并可选一个或多个加料。

### ER 表达

- `ProductSpecification` 决定商品允许哪些规格及当前差价。
- `SpecificationIngredient` 决定具体商品规格对各基础配方原料的系数。
- `ItemSpec` 保存成交时每种类型的选项、名称和差价快照。
- `AddOn` 定义加料当前价格和每份用量，`ItemAddOn` 保存成交快照。

### 核对结论

- `PK(item_id, spec_type)` 保证同一明细同类型最多一项。
- 下单过程检查每个开放类型必须明确选择，默认选项也要传入。
- 同一加料在一条明细最多一行；不同配置必须拆成不同明细。
- 场景能够表达，并且当前配置与历史选择职责分离。

## 6. 场景五：库存扣减、历史消耗和退款

### 正常路径

```text
Recipe 基础用量
× SpecificationIngredient 各类型系数
+ AddOn.extra_amount
× OrderItem.quantity
→ 按 item_id、ingredient_id 保存 OrderItemIngredient
→ 按 ingredient_id 汇总整单需求
→ 检查并扣减 Ingredient.stock
```

退款只读取 `OrderItemIngredient.amount` 返库，不重新读取已改变的配方、系数或加料定义。

### 核对结论

- 历史快照设计可以保持退款语义。
- 整单库存汇总、扣减和订单写入在同一事务中。
- 当前过程能保证整单至少有原料需求，但未逐 `item_id` 保证快照非空；这是明确的未通过设计检查项。

## 7. 场景六：多人同时值班

### 输入场景

员工 E001 和 E002 的值班区间同时覆盖订单 O001 的 `order_time`。

### ER 表达

```text
Employee 1 → 0..N DutyRoster
DutyRoster 0..N ⇢ 0..N SalesOrder
匹配条件：start_time <= order_time < end_time
```

### 核对结论

- 一名员工一段值班一行，多人同时值班保存多行。
- 订单不保存单一 `employee_id`，因此可以得到完整团队。
- 这是时间条件推导联系，不是数据库外键；图中必须使用虚线。
- 未匹配值班记录的订单应保留在诊断查询中，不能自动解释为“无人参与”。

## 8. 设计检查汇总

| 检查项 | 结果 | 说明 |
|---|---|---|
| 多商品与重复商品不同配置 | 通过 | 独立 `item_id`，无错误唯一约束 |
| 会员可选参与订单 | 通过 | 可空会员 FK + 归属互斥 CHECK |
| 游客不建业务档案 | 通过 | UUID 归属 + 技术身份绑定 |
| 商品—规格、商品—原料 M:N 分解 | 通过 | 关联实体携带价格、用量和系数 |
| 交易快照与当前配置分离 | 通过 | 多个快照属性/实体 |
| 多人值班团队 | 通过 | 时间区间推导 M:N |
| 订单至少一条明细 | 过程实现 | 表级 FK 本身不能保证 |
| 每条明细至少一条消耗快照 | **未通过** | 当前只有整单非空检查 |
| 可编辑 ER 源 | 通过 | 已补建 Mermaid 源；PNG 为清晰导出图 |
| 数据库本轮实证 | **通过** | 已按冻结 SQL 重建；对象、44/44、84/84、数据、查询和 CRUD 回滚均通过 |

## 9. 当前数据库交叉验证
