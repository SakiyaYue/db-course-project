# v0.1 实体、属性与码分析

分析依据：`db_creation.sql`、`constraint.sql`、`role.sql`、第一阶段数据字典和对象清单。本文描述完整安装后的 v0.1 逻辑模型，不把尚未确认的 v1.0 改造方案写成现状。

## 1. 对象分类原则

- **独立业务实体**：有独立生命周期和业务标识，不仅用于连接其他对象。
- **业务事件/聚合实体**：记录一次发生过的业务事实，例如订单和值班区间。
- **关联或配置实体**：把 M:N 联系分解为可保存的关系，并携带联系本身的属性。
- **历史快照实体或属性**：保存成交时事实，不能用当前主数据重算覆盖。
- **技术辅助对象**：服务于认证、授权或实现，不等于新的顾客业务实体。

名称不默认唯一。只有当前业务规则和数据库唯一约束共同支持的最小属性集才列为候选码；为外键引用建立的非最小唯一组合不列为候选码。

## 2. 逐表分析

### 2.1 `dbo.Member`：会员

- 分类：独立业务实体。
- 一行含义：本店的一名会员及其当前联系信息和积分余额。
- 主码：`member_id`。
- 其他候选码：`phone`。
- 外码：无。
- 保留理由：会员有独立生命周期，同一会员可以有零笔或多笔订单；积分是当前业务状态。
- 注意：手机号唯一是本项目简化规则，不证明号码真实可用；会员名称不是候选码。

### 2.2 `dbo.Employee`：员工

- 分类：独立业务实体。
- 一行含义：本店的一名员工及其当前在职状态、月薪和业务岗位。
- 主码：`employee_id`。
- 其他候选码：无。
- 外码：无。
- 保留理由：员工独立于排班和订单存在；一名员工可以有多段值班记录。
- 注意：`role` 是店员/店长业务岗位，不等于 SQL Server 数据库角色成员关系。

### 2.3 `dbo.DutyRoster`：单人值班记录

- 分类：业务事件实体，兼具员工与时间区间的联系含义。
- 一行含义：一名员工在 `[start_time, end_time)` 时间段内值班。
- 主码：`duty_id`。
- 其他候选码：`(employee_id, start_time)`。
- 第 6 周补充：在同员工非空值班区间不重叠的业务规则下，`(employee_id, end_time)` 也是候选码；它由过程规则推导，未显式声明 UNIQUE。详见[函数依赖分析](../06-normalization/函数依赖与范式分析.md)。
- 外码：`employee_id → Employee.employee_id`。
- 保留理由：值班本身有时间属性和历史价值，不应只作为订单上的一个员工字段。
- 注意：同一员工区间不重叠由 `usp_SaveDutyRoster` 检查，单靠候选码不能阻止不同开始时间的重叠区间。

### 2.4 `dbo.Product`：商品

- 分类：独立业务实体。
- 一行含义：一种可配置销售的饮品/商品及其当前名称、基础价和上下架状态。
- 主码：`product_id`。
- 其他候选码：无。
- 外码：无。
- 保留理由：商品是配方、规格配置和订单明细的共同父对象。
- 注意：`product_name` 允许重复，不是候选码；历史订单读取名称快照而非当前名称。

### 2.5 `dbo.Ingredient`：原料与当前库存

- 分类：独立业务实体和当前状态实体。
- 一行含义：一种原料、统一计量单位、当前库存和可用状态。
- 主码：`ingredient_id`。
- 其他候选码：无。
- 外码：无。
- 保留理由：单门店范围下，原料主数据与当前库存是一对一状态，暂不需要拆成只有原料编号和数量的独立库存表。
- 注意：`ingredient_name` 不唯一；计量单位被配方或历史快照引用后不能随意修改。

### 2.6 `dbo.Specification`：规格选项

- 分类：独立配置实体。
- 一行含义：一种规格类型中的一个选项，例如糖度、温度或杯型中的具体选项。
- 主码：`spec_id`。
- 其他候选码：`(spec_type, spec_name)`。
- 外码：无。
- 非候选唯一组合：`(spec_id, spec_type)`。由于 `spec_id` 已能唯一标识记录，该组合不是最小超码，只为 `ItemSpec` 的复合外键核对类型而保留。

### 2.7 `dbo.AddOn`：加料定义

- 分类：独立配置实体，但每种加料依赖一种原料。
- 一行含义：一种可选加料的当前名称、价格、对应原料、每份用量和状态。
- 主码：`addon_id`。
- 其他候选码：`addon_name`。
- 外码：`ingredient_id → Ingredient.ingredient_id`。
- 保留理由：加料价格和每份用量属于加料定义，不属于订单明细或基础配方。

### 2.8 `dbo.SalesOrder`：正式订单

- 分类：业务事件和交易聚合根。
- 一行含义：一次已正式创建的购买交易及其归属、创建时间、成交总额和当前状态。
- 主码：`order_id`。
- 其他候选码：无。
- 外码：`member_id → Member.member_id`。
- 归属规则：`member_id` 与 `guest_id` 必须且只能有一个非空；`guest_id` 不是外码，也不唯一，同一游客会话可有多笔订单。
- 保留理由：订单总额和状态属于交易整体；订单明细、退款和积分流程都以订单为边界。

### 2.9 `dbo.OrderItem`：订单明细

- 分类：订单拥有的交易明细实体，含核心历史快照。
- 一行含义：一笔订单中一种确定配置的商品购买行及其杯数、成交价和小计。
- 主码：`item_id`。
- 其他候选码：无。
- 外码：`order_id → SalesOrder.order_id`；`product_id → Product.product_id`。
- 历史属性：`product_name_snapshot`、`base_price_snapshot`、`unit_price`；`sub_amount` 是持久化计算列。
- 注意：不能假设 `(order_id, product_id)` 唯一；同一商品以不同规格/加料可以在同一订单出现多次。

### 2.10 `dbo.ProductSpecification`：商品规格配置

- 分类：`Product` 与 `Specification` 的关联/配置实体。
- 一行含义：某商品是否支持某规格选项，以及该选项的当前每杯差价和状态。
- 主码：`(product_id, spec_id)`。
- 其他候选码：无。
- 外码：`product_id → Product`；`spec_id → Specification`。
- 联合码作用：同一商品对同一规格选项最多一条当前配置。

### 2.11 `dbo.Recipe`：基础配方

- 分类：`Product` 与 `Ingredient` 的关联/配置实体。
- 一行含义：某商品每杯基础配方中一种原料的基础用量。
- 主码：`(product_id, ingredient_id)`。
- 其他候选码：无。
- 外码：`product_id → Product`；`ingredient_id → Ingredient`。
- 联合码作用：同一商品的同一种基础原料只能有一条基础用量。
- 保留理由：商品和原料是 M:N；配方行携带 `base_amount`，不能只用无属性连线表示。

### 2.12 `dbo.SpecificationIngredient`：商品规格原料系数

- 分类：三元配置实体，连接商品规格配置、商品配方原料和原料。
- 一行含义：某商品选择某规格时，对该商品基础配方中某一种原料应用的系数。
- 主码：`(product_id, spec_id, ingredient_id)`。
- 其他候选码：无。
- 外码：`(product_id, spec_id) → ProductSpecification`；`ingredient_id → Ingredient`；`(product_id, ingredient_id) → Recipe`。
- 联合码作用：同一商品、规格和原料组合最多一条系数规则。
- 保留理由：同一“大杯”选项在不同商品上可调整不同原料，且一个选项可同时调整多种原料。

### 2.13 `dbo.ItemSpec`：明细规格快照

- 分类：`OrderItem` 与 `Specification` 的历史关联实体。
- 一行含义：某条订单明细在成交时选择的一种规格类型、具体选项、名称和价格差快照。
- 主码：`(item_id, spec_type)`。
- 其他候选码：`(item_id, spec_id)`，由 `spec_id → spec_type`、主码和复合外键共同推导，未单独声明 UNIQUE。
- 外码：`item_id → OrderItem`；`(spec_id, spec_type) → Specification(spec_id, spec_type)`。
- 联合码作用：一条明细每种规格类型最多一个选项。
- 历史属性：`spec_name_snapshot`、`price_delta_snapshot`。

### 2.14 `dbo.ItemAddOn`：明细加料快照

- 分类：`OrderItem` 与 `AddOn` 的历史关联实体。
- 一行含义：某条订单明细成交时选择的一种加料及其名称、价格快照。
- 主码：`(item_id, addon_id)`。
- 其他候选码：无。
- 外码：`item_id → OrderItem`；`addon_id → AddOn`。
- 联合码作用：同一明细同一种加料最多选择一次；杯数沿用 `OrderItem.quantity`。

### 2.15 `dbo.OrderItemIngredient`：明细原料消耗快照

- 分类：历史消耗快照关联实体。
- 一行含义：某条订单明细的全部杯数在付款时实际扣减的一种原料总量。
- 主码：`(item_id, ingredient_id)`。
- 其他候选码：无。
- 外码：`item_id → OrderItem`；`ingredient_id → Ingredient`。
- 联合码作用：同一明细的同一种原料在合并基础配方和加料后只保存一行。
- 保留理由：退款必须按历史实际扣减量返库，不能按当前配方重算。

### 2.16 `teabar_auth.PrincipalBinding`：数据库身份绑定

- 分类：技术授权辅助对象，不是顾客业务档案。
- 一行含义：一个数据库 principal SID 与一个会员身份或游客 UUID 的活动绑定。
- 主码：`principal_sid`。
- 其他候选码：`principal_name`。
- 外码：`member_id → dbo.Member.member_id`。
- 归属规则：`member_id` 与 `guest_id` 二择一。
- 保留理由：数据库内部演示需要可信身份来源，不能让调用者自行传入他人的会员或游客归属。
- 注意：当前没有限制一个会员只能绑定一个 principal；真实 Web 认证和会话模型尚未确定。

## 3. 保留与待审查结论

### 当前有明确保留理由

- 交易名称、价格、规格、加料和原料消耗快照：用于历史可追溯与退款，不是应简单消除的重复。
- `SalesOrder.total_amount`：交易整体成交金额，必须由受控流程维护并用明细汇总回归检查。
- `Ingredient.stock`：单门店当前业务状态，现阶段与原料主数据一对一。
- 订单不保存单一员工外码：多人同时值班，通过时间区间推导团队更符合当前业务规则。
- 多个联合主码：表达关联对象在业务上的最小唯一性，不应为了“看起来简单”统一改成自增代理键。

### 必须后续确认

- 每条明细是否必须至少有一条非零消耗快照；
- 字符串订单、明细和值班编号由哪一层生成；
- 规格选项、系数、加价和配方样例是否代表最终业务规则；
- Web 登录主体与数据库 principal、角色及购买身份如何映射；
- `PrincipalBinding` 是否仍适合作为实际应用安全模型。
