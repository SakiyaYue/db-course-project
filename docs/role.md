# 第四周：role.sql 角色权限设计要求

本文件记录已确认的角色权限设计，并同步独立 `role.sql` 的实现与验证状态。第 1—13 节为设计要求，第 14 节为当前复现与验证说明。数据完整性要求见 [constraint.md](constraint.md)。

## 1. 授权原则

创建顾客、会员、店员、店长四种数据库角色，授予完成各自职责所需的最小权限，并使用不同测试用户验证正常操作和越权失败。

查询通过限定数据范围的视图或查询操作实现；写入通过指定的受控业务操作实现。不能为了方便向业务角色授予数据库所有权限，也不能用“只能查看”的简化取消顾客和会员的下单付款能力。

订单、库存和积分不能靠任意修改表字段完成业务操作。角色授权和业务校验必须同时成立：有权办理退款，也仍然只能退符合条件的订单。

## 2. 四种角色的职责

| 角色 | 允许的主要行为 | 数据范围和限制 |
|---|---|---|
| 顾客 | 浏览商品、选择规格和加料、下单付款、查看本人订单、申请并执行符合条件的本人订单退款 | 只能访问本人临时会话归属的订单；不能查看他人订单、会员名单和员工工资 |
| 会员 | 顾客的购买能力，以及查看本人会员资料、积分和消费记录 | 只能访问本人会员身份的资料和订单；不能自行修改积分或操作他人订单 |
| 店员 | 接收已付款订单，推进制作、待取餐和完成；协助退款；登记会员、更正会员姓名和手机号 | 订单查询限定为当天订单及全部未完成订单；不能代替顾客下单、改价、补库存、读取员工工资或管理数据库授权 |
| 店长 | 店员的工作操作，以及管理商品、配方、规格、加料、原料、库存、员工、值班；查询经营统计 | 可以查全部历史订单；仍不能任意改历史订单、快照或积分，不能物理删除核心记录，不能授予数据库权限 |

顾客和会员是购买者；店员处理已经下单付款的订单。店长的管理权限也通过规定操作执行，不等于对全部业务表拥有任意增删改权限。

## 3. 购买身份与本人数据

### 3.1 游客身份

非会员使用系统生成的临时 guest_id，不要求注册会员，也不要求提交姓名或手机号。不新增顾客业务资料表。

同一次顾客会话共用一个临时 ID，可以关联多笔订单，刷新页面仍保留身份。会话结束后，订单中的 ID 保留为历史记录。

### 3.2 会员身份

会员使用已经认证和绑定的 member_id，查询本人资料、积分以及消费记录。会员权限不代表可以查看会员表中的全部记录。

### 3.3 归属不能由调用者任意指定

下单操作应从当前可信身份取得订单归属，不能让调用者自行填写他人的会员编号或游客编号。

查询和退款都核对当前身份与订单归属。即使知道他人的订单编号或临时 ID，也不能访问或退款他人的订单。

身份绑定方式属于实现细节，但必须由数据库管理员或可信系统维护，不能开放给顾客、会员、店员或店长自行更改。不得仅信任调用者传入的编号作为身份认证。

## 4. 顾客和会员的下单付款

购买流程保持原讨论的业务顺序：

1. 浏览商品并选择规格和加料。
2. 根据当前商品配置计算价格及最终原料需求。
3. 检查整笔订单是否有足够库存。
4. 支付成功后创建正式订单、明细、选择记录和成交快照，并扣减库存。
5. 订单进入“排队中”，由店员接单制作。

付款前不持久化正式订单。课程原型可以模拟支付成功，不要求接入真实支付平台；模拟与真实支付应明确区分。

受控下单操作需要保证：

- 至少有一条明细，杯数是正整数。
- 只能购买在售商品、可用规格和加料；实际需要的原料必须可用且库存充足。
- 商品每种开放规格类型必须明确选择一项，默认选项也要保存。
- 同类型不能重复选，所选选项必须属于该商品的可用配置。
- 价格在受控操作中计算，不能直接接受调用者任意指定的成交金额。
- 多个规格对同一原料的系数相乘，独立加料不乘规格系数。
- 同一原料的配方与加料消耗合并；汇总全部明细后核对整单库存。
- 原料用量按规定精度保存，计件原料每杯用量必须为整数。
- 创建整单、保存快照与扣库一起成功或一起失败，不能留下半张订单。
- 不得因重复提交订单编号而重复扣库存。

## 5. 店员的订单查询范围

店员可以查询以下集合的并集：

- 当天的全部订单，用于制作、交付和当天核对。
- 所有仍在排队中、制作中、待取餐的订单，不受下单日期限制。

例如昨天仍未交付的订单可以查；昨天已经完成或取消的订单不在店员的查询范围中。当天已完成或取消的订单仍可用于当天核对。

店长可以查询全部历史订单及经营统计。会员可以查询本人的历史订单，不受店员的当天范围限制。顾客只能访问当前临时身份归属的订单。

订单详情、规格、加料和制作所需原料消耗的查询应继承同一订单范围，不能通过另一张明细表绕过限制。店员读取值班团队时，不应获得员工工资字段。

## 6. 制作与交付操作

店员和店长通过指定操作推进状态：

| 操作 | 允许的原状态 | 新状态 |
|---|---|---|
| 接单开始制作 | 排队中 | 制作中 |
| 制作完成 | 制作中 | 待取餐 |
| 顾客取餐、完成交付 | 待取餐 | 已完成 |

不能从排队中直接完成，不能把已完成改回制作中，也不能重复完成并重复结算积分。

不授予任意更新订单状态列的权限。仅限制状态列可写，仍然可能跳过流程，不符合本次选择的操作级授权方案。

## 7. 退款权限和返库

| 操作者 | 可以办理的退款 |
|---|---|
| 顾客 | 本人临时身份的排队中订单 |
| 会员 | 本人会员身份的排队中订单 |
| 店员 | 工作订单范围中符合条件的订单，可协助顾客或会员办理 |
| 店长 | 符合条件的订单，可协助顾客或会员办理 |

制作中及之后不允许退款。已经取消的订单不能重复退款、重复返库。

退款取消与恢复库存必须在同一事务完成。恢复量依据付款时保存的原料消耗快照，不重读当前商品配方、规格系数或加料用量。退款后保留订单、明细、成交金额及快照，状态记为“已取消”。

## 8. 会员登记、资料修改和积分

店员和店长均可登记会员、更正姓名和手机号，但这些操作不能修改积分。

新会员积分从 0 开始。积分按整笔订单总金额向下取整后增加，每整元积 1 分，例如 19.80 元积 19 分；不对每条明细分别取整。

只有订单首次完成才结算积分。支付后尚未完成、退款取消、重复完成均不增加积分。非会员订单不结算会员积分。

订单完成与积分更新在同一事务中处理；顾客、会员、店员和店长均不获得直接修改积分的权限。

## 9. 店长的库存管理

店长通过两个明确区分的操作管理库存：

| 操作 | 参数含义 | 数量限制 |
|---|---|---|
| 补库存 | 在当前库存上增加的数量 | 必须大于 0 |
| 盘点修正 | 盘点确认的实际剩余库存 | 必须大于或等于 0 |

以“个”为单位的原料，补库和盘点参数都必须是整数。不能把“补 500 克”和“实际剩 500 克”混为同一个操作。

不授予店长直接修改库存列的权限；店员没有补库和盘点权限。订单扣减、退款恢复也通过对应订单操作完成。

## 10. 店长的资料与配置管理

店长可以管理商品价格、名称、上下架状态，维护原料、配方、规格、商品规格配置、原料系数、加料、员工资料及值班安排。

管理操作仍需满足完整性和业务要求：

- 改当前商品价格不改变历史成交金额和快照。
- 修改配方和规格规则不改变付款时的消耗快照。
- 规格规则只能调整该商品基础配方中的原料。
- 删除或更换被引用的配方原料前，先处理相应规格原料规则。
- 计件原料的配方、加料及调整后的每杯用量必须为整数。
- 启用商品规格时，每种类型各选一个可用选项，检查全部糖度、温度、杯型组合的计件用量；不能只检查单个系数。同类型备选不相乘，停用选项不参与组合。没有可用选项的类型在配置维护阶段暂按系数 1 检查，上架和下单仍要求每种已配置类型有可用且明确选择的选项。
- 已使用的原料不能直接变更计量单位，避免历史数量含义改变。
- 同一员工的值班时间不能重叠；不同员工可以同时值班，首尾相接的班次允许。
- 规则尚未完成的商品规格配置保持停用，完成定义后再启用。

配方和规格关联的调整属于规定的维护操作，不等于允许任意删除核心业务记录。

## 11. 删除与历史修改限制

本次选择不向业务角色开放商品、原料、会员、员工和历史订单的物理删除权限，即使资料尚未被引用也不开放。

商品停售通过下架处理，员工离职通过状态变更处理，商品规格通过停用处理。其他核心资料和历史数据保留。

店长也不能绕过受控操作直接修改历史成交金额、名称和价格快照、原料消耗快照或任意改订单状态。管理员进行实验初始化、测试回滚等操作，与业务角色的日常权限区分。

## 12. 员工资料与数据库权限分开维护

Employee.role 表示店员或店长岗位，Employee.status 表示在职或离职。它们是业务字段，不等于 SQL Server 数据库角色成员关系。

| 事项 | 负责者 |
|---|---|
| 员工姓名、月薪、岗位、在职状态及排班资料 | 店长，通过业务管理操作维护 |
| 创建数据库用户、绑定购买身份、加入或退出数据库角色 | 数据库管理员 |
| 员工升职、降职对应的数据库权限调整 | 数据库管理员另行维护 |
| 员工离职后的数据库权限撤销 | 数据库管理员另行维护 |

修改员工表中的岗位或离职状态不会自动改变数据库权限。本周不实现自动同步，应在复现说明中明确管理员的维护步骤。店长角色本身没有授权其他用户或管理数据库角色的权限。

## 13. 权限验证要求

使用两名不同顾客、两名不同会员、店员和店长等测试身份，验证角色差异和同角色不同身份之间的隔离。业务角色不应通过数据库管理员身份执行测试，否则不能证明越权被拒绝。

| 测试场景 | 预期结果 |
|---|---|
| 顾客或会员按合法配置模拟付款下单 | 成功创建正式订单和快照，并正确扣库 |
| 顾客读取本人订单，读取另一个游客的订单 | 前者允许；后者拒绝或查询不到 |
| 会员读取本人资料及订单，读取另一会员资料及订单 | 前者允许；后者拒绝或查询不到 |
| 伪造他人的身份编号申请查询、下单或退款 | 不得绕过可信身份绑定 |
| 店员查询当天订单及昨天未完成订单 | 允许 |
| 店员查询昨天已完成订单、完整会员名单、员工工资 | 不允许 |
| 店长查询全部历史订单和经营统计 | 允许 |
| 店员推进正常制作流程 | 允许 |
| 店员代替顾客下单、直接改价格或直接补库存 | 不允许 |
| 跳过状态直接完成、已完成重新制作、重复完成 | 拒绝，不能重复加积分 |
| 顾客退款本人排队订单，店员或店长协助合法退款 | 允许，按原消耗快照恢复库存 |
| 他人订单退款、制作中退款、重复退款 | 拒绝，不能错误返库 |
| 店长通过补库与盘点管理库存 | 合法参数允许；负数、零补库、非整数计件数量拒绝 |
| 店员或店长登记会员及更正姓名、手机号 | 允许，新会员积分为 0，原会员积分不被更改 |
| 会员自行改积分，店长直接改历史快照或删核心记录 | 不允许 |
| 店长修改员工业务岗位或离职状态 | 允许，但数据库角色成员不自动变化 |
| 店长自行创建授权、将用户加入数据库角色 | 不允许 |
| 缺规格、停用规格、库存不足、重复订单编号 | 拒绝，不留下半张订单或额外库存变化 |
| 各单项调整为整数，但两类型或三类型组合产生非整数计件用量 | 启用配置时拒绝，本次价格、状态修改全部回滚；修正系数后允许启用和下单 |

失败用例需要确认拒绝原因，并核对没有留下部分业务数据变化。验证结束恢复测试数据、身份绑定和执行上下文；角色、用户及授权定义可以保留用于后续演示。

## 14. 当前实现与复现说明

管理员按 `db_creation.sql` → `seed_data.sql` → `constraint.sql` → `role.sql` 顺序准备课程数据库。建库脚本会删除并重建 TeabarDB，仅用于首次初始化或明确需要重置的场景；已有数据需先核对结构。角色脚本在无未结束事务的新窗口完整执行，可重复运行，不重建数据库。

`role.sql` 创建四种数据库角色、两名游客、两名会员、店员和店长共六个 `WITHOUT LOGIN` 演示用户。查询通过 `teabar_api` 视图实现购买者本人范围和店员工作范围；店长可以读取全部经营数据。写入通过下单、制作流转、退款、会员登记、补库与盘点、商品及配置、员工与排班维护过程实现。各业务角色不能直接写业务表或维护 `teabar_auth.PrincipalBinding`，店长也不能授予数据库权限。

身份从管理员维护的数据库用户 SID 绑定取得；下单接口没有会员编号、游客编号和成交总额参数，也不信任客户端 SESSION_CONTEXT。演示游客重复下单复用绑定 ID；真实前端的注册、认证及游客会话结束后的绑定生命周期需要可信后端维护。付款成功参数仅用于课程模拟。

`usp_SaveProductSpecification` 锁定商品行，使同商品的配置启用操作串行执行。单项检查后，将本次配置变更纳入全部可用选项，按类型组合并相乘，检查计件原料的每杯基础部分。非法组合抛出 52116，并在同一事务或保存点内回滚本次配置修改；下单过程保留最终用量检查。已完成定义的选项未配置某原料系数时按 1 处理。

2026-10-06 独立 SQL Server 测试库验证：84/84 个正常、越权及业务用例通过，重复执行通过。新增 10 个用例验证 `2 × 1.5 × 1.5 = 4.5`、`4 × 1.5 × 1.5 × 1.5 = 13.5` 时拒绝启用，同类型备选与停用选项不相乘、零系数不掩盖其他非法组合，以及修正后合法两类型和三类型订单分别保存 6 个、18 个的消耗快照，整单扣库 24 个。反例同时核对错误号及操作前后的业务数据哈希，不能把无关错误或部分数据变化当成通过。

除脚本中带外层事务的保存点验证外，还单独验证了无外层事务的非法组合启用：错误为 52116，配置价格与状态恢复，事务计数归零。现有 view.sql、query.sql 和 crud_demo.sql 在角色安装后执行通过。

验证事务结束回滚业务数据与临时会员绑定，恢复管理员上下文；安装的角色、用户、权限、视图和过程保留用于演示。员工岗位或离职状态不会自动改变数据库权限，管理员另行执行退角色和加角色操作，例如离职时 `ALTER ROLE teabar_clerk DROP MEMBER demo_clerk;`，升降职先退旧角色再加新角色。本次仅验证独立测试库，没有升级现有 TeabarDB。
