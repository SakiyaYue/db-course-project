# SSMS 19 建库与 CRUD 操作说明

第三周脚本按作业产出拆分：`db_creation.sql` 创建数据库和 15 张表，`seed_data.sql` 装载 232 条初始化样例，`crud_demo.sql` 在这批样例上演示增删改查，`query.sql` 提供只读查询。现场截图已按类别归档，见[结果目录](../figure/README.md)。

## 1. 连接 SQL Server

SSMS 是管理工具，数据保存在 SQL Server 实例里。本机使用默认实例 `localhost`，选择“Windows 身份验证”连接；也可以使用服务器名 `DESKTOP-7H8JJ9K`。其他电脑应填写自己的实例名，安装 SQLEXPRESS 的电脑可使用 `.\SQLEXPRESS`。

[官方连接和查询说明](https://learn.microsoft.com/en-us/ssms/quickstarts/ssms-connect-query-sql-server)

此前检查时本机 TeabarDB 已有 15 张表和 232 条样例，但小计仍是普通列，规格类型仍为“冰量”。编辑文件不会自动升级已建数据库。新版 CRUD 要求目标库使用小计计算列、温度类型，并已装载 `seed_data.sql` 中的样例。本次约束与角色修正使用独立测试库验证，未升级现有 TeabarDB；执行前应核对目标库结构。

## 2. 建库及建表

**`db_creation.sql` 会强制断开已有 TeabarDB 的连接、删除整个库，再重新创建。仅在首次建库或确认需要重置课程数据时完整运行；需要保留已有数据时应通过迁移更新结构。**

1. 在 SSMS 选择“文件 → 打开 → 文件”，打开根目录的 `db_creation.sql`。
2. 确认连接正确，不选中局部文本，按 F5 完整执行。查看“消息”，确认所有批次没有错误。
3. 刷新“数据库”，展开 `TeabarDB → 表`，应看到 15 张表；此时各表均为空。
4. 建库文件已显式设置持久化计算列所需会话选项，小计按单价乘数量自动计算。

`GO` 是 SSMS 的批次分隔标记，保留独立行即可。如果通过 SSMS 手工创建空 TeabarDB，只执行文件中 `USE TeabarDB` 之后的会话设置和建表部分，再按下一节装载样例。

## 3. 装载样例数据

打开并完整执行 `seed_data.sql`。文件只负责 INSERT，不创建或清空表；要求全部 15 张业务表为空，并在一个事务内完成全部装载。成功后显示“初始化样例装载成功”；任一步失败都会回滚本次插入。重复装载会报错，不覆盖已有记录。

装载后可以检查：

```sql
USE TeabarDB;
GO
SELECT name FROM sys.tables WHERE is_ms_shipped = 0 ORDER BY name; -- 15 张表
SELECT COUNT(*) AS product_count FROM dbo.Product;        -- 4
SELECT COUNT(*) AS ingredient_count FROM dbo.Ingredient;  -- 9
SELECT COUNT(*) AS order_count FROM dbo.SalesOrder;        -- 5
SELECT COUNT(*) AS order_item_count FROM dbo.OrderItem;    -- 7
```

样例保留商品、会员、员工、排班、配方、规格、加料、订单和原料消耗之间的联系。库存是样例剩余库存，历史订单装载时不再扣一次；会员积分是样例期初余额。

### 3.1 安装第四周约束与角色

管理员在无未结束事务的新窗口依次完整执行 `constraint.sql` → `role.sql`。约束验证应为 44/44 通过，角色及业务验证应为 84/84 通过；两文件可重复执行。验证记录回滚，约束、角色、演示用户和接口保留。角色脚本额外创建身份绑定表，前面的 15 张表是装载样例时的业务表数量。

随后执行 `view.sql` → `query.sql` → `crud_demo.sql` → `query.sql` 完成展示。CRUD 直接写表演示由管理员执行；顾客、会员、店员、店长通过 `teabar_api` 受控操作执行各自业务。规格启用时检查全部可用类型组合的计件用量，非法组合提前拒绝；具体复现、模拟身份与支付范围、员工离职撤权步骤见 [角色说明](role.md) 和 [约束说明](constraint.md)。

## 4. 运行 CRUD 演示

在没有未结束事务的新查询窗口中打开 `crud_demo.sql`，按 F5 完整执行。脚本在一个事务内操作，正常结束或出错均回滚；不要只执行局部 INSERT、UPDATE 或 DELETE。

新增测试商品 CP001 参考原商品 P001 的名称和价格，保持下架；新增测试原料 CI001 参考原料 I001 的名称和单位。改价及上下架直接操作原商品 P001，补库直接操作原料 I001。取消分支 CO001／CT001 和完成分支 CO002／CT002 使用已有会员 M001、商品 P001、加料 A001，以及现有商品规格 S002／S005／S008；不再另造测试会员、加料或一套测试配方。

| 对象 | 新增与查询 | 修改 | 删除 |
| --- | --- | --- | --- |
| 商品 | 从样例 P001 新增 CP001；查询原样例及历史成交快照 | P001 改价 6 → 7 元，并演示在售 → 下架 → 在售；历史成交快照不变 | 删除本次新增且没有引用的 CP001 |
| 原料库存 | 从样例 I001 新增 CI001；查询原柠檬库存 | I001 补货 5000 → 5200g；下单后 5075g；取消后 5200g | 删除本次新增且没有引用的 CI001 |
| 订单 | 新增 CO001、CO002，关联 M001、P001 及同一套规格加料 | CO001 排队取消并返库；CO002 待取餐完成并结算积分 | 清理 CO001 及子记录；CO002 保留到最终回滚 |
| 会员 | 查询原会员 M001 和积分 | CO002 首次完成后 120 → 140 分；重复完成和取消不加分 | 保留会员，最终回滚积分 |
| 员工与排班 | 按订单时间查询当时全部值班员工，展示交接前后团队 | 只查询归属，不修改员工或排班 | 保留已有员工和排班 |

新订单为 2 杯冰鲜柠檬水，五分糖、少冰、大杯并加芋圆。改价后基础价 7 元，大杯加 2 元，加芋圆 1 元，成交单价 10 元，总额 20 元。只汇总实际选中的规格加价，不累加所有可选规格。

基础配方按所选糖度、温度和杯型的原料系数相乘；加料按每杯一份额外计算，同原料用量先合并再保存。初始化样例下，消耗及库存结果为：

| 原料 | 消耗 | 下单前库存 | 下单后库存 | 取消后库存 |
| --- | --- | --- | --- | --- |
| I001 柠檬 | 125g | 5200g | 5075g | 5200g |
| I002 糖浆 | 37.5ml | 10000ml | 9962.5ml | 10000ml |
| I009 茉莉绿茶汤 | 500ml | 15000ml | 14500ml | 15000ml |
| I007 冰块 | 125g | 20000g | 19875g | 20000g |
| I006 芋圆 | 100g | 4000g | 3900g | 4000g |

上述库存表展示取消分支 CO001 的扣返库。随后 CO002 使用同样配置再次扣库；订单完成后保留这次消耗，柠檬最终为 5075g，其他原料为表中的“下单后库存”。完成不会返库；最终事务回滚才恢复全部原始库存和补货操作。

商品上下架使用已有配方和规格的 P001。下架后查询“在售商品”时 P001 返回 0 行，重新上架后继续用于测试订单；未配置配方的测试新品 CP001 保持下架。

积分结算沿用数据字典中的实现假设：完成订单金额向下取整，消费 1 元积 1 分。CO002 直接准备为“待取餐”，省略展示前面的制作状态，只演示完成操作。UPDATE 限定待取餐状态，并通过 OUTPUT 保存本次首次完成的订单；会员只对该集合加分，状态更新和积分结算在同一个事务中。20 元订单增加 20 分，M001 从 120 变为 140；再次使用相同完成条件更新 0 行，不再结算积分。CO001 取消后积分仍为 120。

团队归属使用 `DutyRoster.start_time <= SalesOrder.order_time AND SalesOrder.order_time < DutyRoster.end_time`，查询全部匹配员工。新测试订单借用 O001 的样例日期，CO002 在其后 5 分钟创建，对应张明 E001、李华 E002；样例 O004 在 16:30 创建，对应张明 E001、王芳 E003。修改脚本中的 `@team_order_id` 可以选择其他订单，同时保留 O004 作为对照。LEFT JOIN 保留未匹配排班的订单，不按员工当前在职状态筛选历史团队。

此团队表示下单时的排班归属；当前模型没有记录各杯饮品的实际制作人，不能据此指定唯一员工负责人。

11 条 UPDATE 和 7 条 DELETE 均有紧邻的同条件 SELECT，联接更新使用相同 FROM／JOIN／WHERE 范围。扣库和返库查询显示操作量及预期库存；条件扣减及行数检查保证原料缺失、不可用或不足时回滚整段演示。

小计定义为 `sub_amount AS CAST(unit_price * quantity AS decimal(10,2)) PERSISTED NOT NULL`，INSERT 时省略小计，改数量或单价后自动重算。整单总额仍由操作流程维护。演示固定使用上述样例配置和积分假设，不处理真实支付。

物理删除仅清理本次新增的 CP001、CI001、CO001、CT001 及其子记录。CO002、CT002 及其快照作为完成订单保留到最终回滚。原样例商品、原料、会员、加料、规格和历史订单均保留。最终回滚恢复 P001 的 6 元价格和在售状态、I001 的 5000g 库存、M001 的 120 积分，同时移除所有测试订单。

截图可以选商品上下架、改价、原料扣返库、完成订单积分、重复完成结果、订单值班团队、删除结果及最终回滚结果。

## 5. 查询与复现顺序

```text
db_creation.sql   建库 + 建表，得到 15 张空表
    ↓
seed_data.sql     装载 232 条初始化样例
    ↓
constraint.sql    安装约束，44 项正反例验证
    ↓
role.sql          安装角色与业务接口，84 项验证
    ↓
view.sql          创建 13 个正式统计与业务视图
    ↓
query.sql         执行 Q01—Q18，查看原样例
    ↓
crud_demo.sql     在样例上新增、查询、修改、删除，结束回滚
    ↓
query.sql         再次确认原始样例恢复
    ↓
view_demo.sql     展示测试视图创建、修改和删除
    ↓
query_demo.sql    简短展示关键词、时间范围及每日经营查询
```

`query.sql` 包含商品、库存、购买试算、订单会员、订单详情、值班团队和经营统计。原样例在 2026-10-04 的已完成销售额为 46 元、3 单、5 杯；`view.sql` 的订单概要验证应返回 5 行，`amount_matches_items` 全部为 1。查询单笔订单时修改对应批次的 `@order_id`，详情查询默认 O001。

重新演示 CRUD 直接再次运行 `crud_demo.sql`；不要重新运行建库或样例脚本。需要完整从空库复现时才从上述第一步开始。

按报告五类实验整理的具体步骤、截图位置与预期结果见[脚本复现与截图清单](脚本复现与截图清单.md)。

## 6. 验证方法与结果

2026-10-05，在本机 SQL Server 的 tempdb 独立 schema 和外层回滚事务中，按拆分后的顺序执行会话设置、建表、样例装载、查询及 CRUD。不执行实际库的 DROP/CREATE DATABASE 段。

验证时把样例事务入口改为保存点，保留其数据在外层测试事务中；CRUD 的事务入口及正常回滚也改为保存点，便于检查前后数据。交付脚本仍使用完整事务，样例成功提交，CRUD 结束回滚。

此前拆分验证通过：DDL 创建 15 张空表，seed_data.sql 加载 232 条原样例，query.sql 返回 13 个结果集；销售额 46 元，两类金额核对均为空。重复装载被错误 51202 拒绝。

新增业务演示后，CRUD 连续运行两次，每次 49 个结果集；上下架、取消返库、完成订单保留消耗、积分 120 → 140、重复完成更新 0 行均正确。CO002 匹配 E001／E002，O004 匹配 E001／E003；11 条 UPDATE 和 7 条 DELETE 的目标查询范围一致。每次回滚后全部 15 张表的行数及行校验和不变。额外验证：20.90 元订单增加 20 分；缺少匹配排班时，订单仍返回并显示“未匹配排班”。全部临时对象最终随外层事务回滚移除。

此前计算列验证已确认 decimal(10,2)、PERSISTED、NOT NULL，改数量和单价后自动重算，默认数量和零价可用，直接写小计及金额溢出被拒绝。此次拆分保留这些定义。

该历史验证不涵盖实际数据库创建权限、通用下单、真实支付、完整制作状态流转或所有并发场景。后续约束、角色及现场复现结果见对应说明与[结果目录](../figure/README.md)，截图待补项在索引中列出。
