## 1 设计约定

- 单门店，不建立门店、总部、供应商、采购或配送表。
- 原料库存存放在 Ingredient.stock 中，单门店下无需另建只有原料编号和库存量的表。
- Recipe 是商品与原料的联系表，每行表示一杯商品使用一种原料的基础用量。
- 已确认手写草图对照清单第 5、6、7 项采用本稿方案：顾客不另建独立表，订单用可空 member_id 区分会员与非会员；规格及加料选择通过 ItemSpec、ItemAddOn 记录在具体明细上；配方采用商品编号、原料编号、每杯基础用量，不另设独立配方编号。
- 正式订单只在支付成功后建立，初始状态为“排队中”，没有“待支付”状态。
- 非会员订单的 member_id 为 NULL。制作由值班团队协作完成，订单不保存单一员工负责人；按订单创建时间匹配值班表，得到当时所有值班员工。
- 值班表每行记录一名员工的一段值班时间；时间匹配采用 start_time <= order_time < end_time，避免相邻班次在交接时刻重复归属。
- 相同商品但规格或加料不同，必须拆成不同订单明细。同一明细的 quantity 杯使用相同配置。
- 已确认规格类型为温度、糖度、杯型，每杯每种类型最多选择一个选项。一种加料对应一种原料，每杯同一种加料最多一份，可以选择多种不同加料；未选加料时无关联记录。
- Specification 保留规格选项定义，AddOn 保留独立加料定义；商品规格原料系数表不替换这两张表，也不实现添加、替换基础原料的操作。
- ProductSpecification 记录商品可选的规格及加价，SpecificationIngredient 按商品、规格选项、原料分别记录系数。同种原料的多个已选规格系数相乘；同一选项在不同商品上可以配置不同系数。
- 手写规格字段中原先无法辨认的文字已确认为“类型”，对应 Specification.spec_type；商品附近规格／加料的连线表达订单明细实际选择了哪些选项，对应 ItemSpec 和 ItemAddOn，不是商品允许哪些选项的适用关系。
- 温度具体选项及其制作、原料规则，杯型具体选项、用量及加价规则尚待确认。现有样例暂用正常冰、少冰、去冰作为温度选项，用中杯作为基础配方对应的杯型；这些选项和系数是演示数据，不代表小组已确认全部规格规则。
- 当前简化版本中，规格原料系数仅作用于基础配方；加料按定义的一份 extra_amount 在调整后相加，不另设随杯型变化的加料规则或商品加料适用配置。
- 金额单位为元，使用 decimal(10,2)；原料用量统一使用 decimal(10,2)，系数使用 decimal(5,2)，单位由 Ingredient.unit 定义。
- 中文字段使用 nvarchar；状态保存中文枚举。日期使用 datetime2(0)，统一按门店所在时区记录。
- 名称不默认具有唯一性。只有已确定能唯一识别记录的业务属性才作为候选码。
- 保存购买时商品、规格、加料名称和价格快照；退款使用付款时保存的原料扣减量，避免配方修改影响退款。
- 默认禁止级联删除历史订单关联数据，商品通过下架、员工通过离职保留记录；原料和加料采用可用／缺货状态，商品规格配置采用可用／停用状态。

会员积分按完成订单金额向下取整后增加，即消费 1 元积 1 分，仍为本设计稿的实现假设。若小组调整规则，应同步修改设计、样例和后续脚本。

`crud_demo.sql` 已沿用此假设，演示待取餐订单首次完成时增加积分、重复完成及取消不增加积分，结束回滚后恢复原会员余额。商品上下架和订单值班团队查询也已加入演示。

## 2 表清单与关系模式

按当前简化方案，共 15 张表：原始 PNG ER 图的 11 张表，加原料消耗快照表、值班表、规格原料系数表和商品规格配置表。Specification、AddOn 均保留；ProductSpecification 管理商品规格配置，SpecificationIngredient 包含 product_id。原始 PNG 中订单直接关联一名员工的设计不再采用。加料按已确认结构保留两张表，不增加新表。

| SQL 表名 | 用途 | 主码 | 其他候选码 | 外码 |
|---|---|---|---|---|
| dbo.Member | 会员资料与积分 | member_id | phone | 无 |
| dbo.Employee | 员工资料与业务角色 | employee_id | 无 | 无 |
| dbo.DutyRoster | 每名员工的值班时间段 | duty_id | (employee_id, start_time) | employee_id |
| dbo.Product | 商品资料与当前售价 | product_id | 无 | 无 |
| dbo.Ingredient | 原料资料与库存 | ingredient_id | 无 | 无 |
| dbo.Recipe | 每杯商品的基础配方 | (product_id, ingredient_id) | 无 | product_id、ingredient_id |
| dbo.Specification | 温度、糖度、杯型选项 | spec_id | (spec_type, spec_name) | 无 |
| dbo.ProductSpecification | 商品可选规格及加价 | (product_id, spec_id) | 无 | product_id、spec_id |
| dbo.SpecificationIngredient | 每个商品规格选项对各原料的系数 | (product_id, spec_id, ingredient_id) | 无 | (product_id, spec_id)、ingredient_id |
| dbo.AddOn | 加料定义与当前价格 | addon_id | addon_name | ingredient_id |
| dbo.SalesOrder | 正式订单 | order_id | 无 | member_id |
| dbo.OrderItem | 订单明细与成交价 | item_id | 无 | order_id、product_id |
| dbo.ItemSpec | 明细选择的规格 | (item_id, spec_type) | 无 | item_id、(spec_id, spec_type) |
| dbo.ItemAddOn | 明细选择的加料 | (item_id, addon_id) | 无 | item_id、addon_id |
| dbo.OrderItemIngredient | 明细原料消耗快照 | (item_id, ingredient_id) | 无 | item_id、ingredient_id |

订单表使用 SalesOrder，避免直接使用 SQL Server 的 ORDER 关键字。主码本身也是候选码；上表“其他候选码”仅列未选作主码的候选码。Specification 的 `(spec_id, spec_type)` 另设 UNIQUE，专门供复合外键引用；因为 spec_id 已唯一，该组合不是最小候选码。

### 联系基数

| 联系 | 正确基数及可选性 |
|---|---|
| Member → SalesOrder | 一个会员有 0..N 个订单；一个订单属于 0..1 个会员 |
| Employee → DutyRoster | 一个员工有 0..N 条值班记录；每条值班记录属于一名员工 |
| SalesOrder ↔ DutyRoster | 按 order_time 落入值班区间匹配；一个订单可匹配多名员工的值班记录，一条值班记录可覆盖多个订单 |
| SalesOrder ↔ Employee | 经值班表和时间条件推导的 M:N 关系，表示订单的值班团队归属，不在订单中保存 employee_id |
| SalesOrder → OrderItem | 一个正式订单应有 1..N 条明细；一条明细属于一个订单 |
| Product → OrderItem | 一个商品被 0..N 条明细引用；一条明细对应一个商品 |
| Product → Recipe | 一个商品有 0..N 条配方行；可售商品必须具有有效配方 |
| Ingredient → Recipe | 一种原料被 0..N 条配方行引用；一条配方行对应一种原料 |
| Product → ProductSpecification | 一个商品有 0..N 条规格配置；每条配置属于一个商品 |
| Specification → ProductSpecification | 一个规格选项可被 0..N 个商品配置使用；每条配置引用一个规格选项 |
| ProductSpecification → SpecificationIngredient | 一条商品规格配置有 0..N 条原料系数规则；每条规则属于一条配置 |
| Ingredient → SpecificationIngredient | 一种原料可被 0..N 条规则引用；每条规则调整一种原料 |
| Ingredient → AddOn | 一种原料可对应 0..N 个加料定义；一个加料对应一种原料 |
| OrderItem → ItemSpec | 一条明细有 0..3 条规格选择；温度、糖度、杯型各最多一条，是否必选或使用默认值待确认 |
| Specification → ItemSpec | 一个规格被 0..N 条选择记录引用；每条记录选择一个规格 |
| OrderItem → ItemAddOn | 一条明细有 0..N 条加料选择；每种加料最多一条 |
| AddOn → ItemAddOn | 一个加料被 0..N 条选择记录引用；每条记录选择一个加料 |
| OrderItem → OrderItemIngredient | 一条明细有多条原料消耗快照；每条快照属于一个明细 |
| Ingredient → OrderItemIngredient | 一种原料可出现在多个历史消耗快照中 |

商品与原料是 M:N，通过 Recipe 表分解为两个 1:N 联系；明细与规格、明细与加料也通过关联表表达 M:N。所有关联表中，一条关联记录只引用父表的一行。

商品与规格选项通过 ProductSpecification 表达 M:N。每条商品规格配置与多种原料通过 SpecificationIngredient 关联。spec_type 只是温度、糖度、杯型的分类，系数绑定具体商品、具体 spec_id 和具体原料；例如不同饮品的“大杯”可以具有不同茶汤系数。这两张表补充配置和计算规则，不替换 Specification 或 AddOn。

订单与值班表使用时间区间连接，不设置 SalesOrder.duty_id，也不设置单一 SalesOrder.employee_id。员工与值班表通过外键连接；订单与值班员工的关系通过查询或视图计算。一条值班记录不是整个团队的一条班次记录，而是一个员工在一个区间内值班的记录。

## 3 字段定义

“默认值 —”表示无默认值；“空”列为“否”表示 NOT NULL。标识符以字母加数字为业务编号示例，但字段域不要求固定前缀。当前编号字段没有自动生成默认值，由脚本或应用分配；明细及值班编号建议沿用字符串，未改为整数 IDENTITY。非空白 CHECK 拒绝空串或仅由普通空格组成的编号及名称。

### 3.1 Member 会员

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| member_id | varchar(10) | 否 | — | PK，非空白 | 会员编号 |
| name | nvarchar(50) | 否 | — | 非空白 | 会员称呼 |
| phone | varchar(20) | 否 | — | UNIQUE，11 位数字且首位为 1；保留 varchar(20) 长度 | 联系电话，会员业务标识 |
| points | int | 否 | 0 | >= 0 | 当前积分 |

phone 的格式规则仅为课程项目的简化校验，不验证号码实际归属或可用性。样例号码为测试数据。

### 3.2 Employee 员工

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| employee_id | varchar(10) | 否 | — | PK，非空白 | 员工编号 |
| name | nvarchar(50) | 否 | — | 非空白 | 员工姓名 |
| status | nvarchar(10) | 否 | 在职 | 在职／离职 | 员工状态 |
| salary | decimal(10,2) | 否 | — | >= 0 | 月薪金额，单位为元／月 |
| role | nvarchar(20) | 否 | — | 店员／店长 | 业务职能 |

员工表按已确认的 ID、姓名、状态、工资、角色五个字段设计，salary 明确记录月薪。role 是业务资料字段，不等于 SQL Server 数据库角色；数据库授权需要另外创建用户、角色并授予权限。当前不扩展工资结算流程。订单对应的多人值班团队继续通过 DutyRoster 和订单时间查询，不由 role 指定单一负责人。

### 3.3 Product 商品

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| product_id | varchar(10) | 否 | — | PK，非空白 | 商品编号 |
| product_name | nvarchar(50) | 否 | — | 非空白 | 商品名称 |
| base_price | decimal(10,2) | 否 | — | >= 0 | 不含额外加料的当前每杯价格 |
| status | nvarchar(10) | 否 | 下架 | 在售／下架 | 人工上架状态 |
| description | nvarchar(200) | 是 | — | 最多 200 字符 | 商品说明 |

缺货由配置及库存计算，不写入 Product.status。新商品默认下架，配方准备好后再上架。

### 3.4 Ingredient 原料与库存

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| ingredient_id | varchar(10) | 否 | — | PK，非空白 | 原料编号 |
| ingredient_name | nvarchar(50) | 否 | — | 非空白 | 原料名称 |
| unit | nvarchar(10) | 否 | — | g／ml／个 | 库存与配方统一计量单位 |
| stock | decimal(10,2) | 否 | 0 | >= 0 | 当前剩余库存 |
| status | nvarchar(10) | 否 | 可用 | 可用／缺货 | 原料当前可用或缺货状态 |

以“个”为单位的原料，库存、配方及实际消耗必须为整数。原料被配方或历史订单引用后禁止直接改变单位；需要换单位时建立新原料编号，避免历史数量失去原含义。

### 3.5 Recipe 基础配方

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| product_id | varchar(10) | 否 | — | 联合 PK，FK → Product.product_id | 商品 |
| ingredient_id | varchar(10) | 否 | — | 联合 PK，FK → Ingredient.ingredient_id | 基础原料 |
| base_amount | decimal(10,2) | 否 | — | > 0 | 每杯基础用量，单位与原料一致 |

联合主键保证同一商品的同一种基础原料只有一行。

此模式已按手写草图对照清单第 7 项确认。原草图中的“编号、原料名、数量”在关系表中明确为 product_id、ingredient_id、base_amount；原料名称通过外键关联 Ingredient 查询，不在 Recipe 中重复保存。Recipe 不单独设置 recipe_id。

### 3.6 Specification 规格

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| spec_id | varchar(10) | 否 | — | PK，非空白 | 规格编号 |
| spec_type | nvarchar(20) | 否 | — | 温度／糖度／杯型 | 规格类型 |
| spec_name | nvarchar(20) | 否 | — | 非空白；与 spec_type 联合 UNIQUE | 规格名称 |

另设 UNIQUE(spec_id, spec_type)，支持 ItemSpec 的复合外键。已确认三种规格类型，每种类型的具体选项及规则尚待审查。Specification 只保存选项的编号、类型、名称；原来的 target_ingredient_id 和 factor 移至 SpecificationIngredient，不在一个规格定义行中限制原料数量。

杯型可以通过多条系数规则调整茶汤、牛奶、糖浆等多种原料，较大杯型的系数可大于 1。温度具体选项及制作方式仍待确定。本版保留统一杯子原料，不设计包装原料替换；杯型加价通过 ProductSpecification 配置，加料按固定的一份用量计算。

本版只处理基础原料的系数调整，不在规格规则中增加 action、replacement_ingredient_id、extra_amount 等字段。额外加料由已确认的 AddOn 和 ItemAddOn 处理。

### 3.7 AddOn 加料

本表结构已确认：每种加料只对应一种原料，价格和用量均按一份定义。PNG 和手写图中的具体加料名称、价格及用量仍只作参考，等待样例审查。

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| addon_id | varchar(10) | 否 | — | PK，非空白 | 加料编号 |
| addon_name | nvarchar(50) | 否 | — | UNIQUE，非空白 | 本店唯一的加料名称 |
| price | decimal(10,2) | 否 | — | >= 0 | 每杯选择一份加料的额外价格 |
| ingredient_id | varchar(10) | 否 | — | FK → Ingredient.ingredient_id | 额外消耗的原料 |
| extra_amount | decimal(10,2) | 否 | — | > 0 | 一份加料的原料用量，单位沿用 Ingredient.unit |
| status | nvarchar(10) | 否 | 可用 | 可用／缺货 | 加料当前可用或缺货状态 |

库存仍保存在 Ingredient 中，不在 AddOn 重复保存。status 采用可用／缺货；缺货时加料不能选择，但不自动使商品基础配方不可售。

### 3.8 SalesOrder 正式订单

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| order_id | varchar(10) | 否 | — | PK，非空白 | 正式订单编号 |
| member_id | varchar(10) | 是 | — | FK → Member.member_id | 会员；非会员为 NULL |
| order_time | datetime2(0) | 否 | SYSDATETIME() | 有效日期时间 | 正式订单创建时间 |
| total_amount | decimal(10,2) | 否 | — | >= 0 | 成交总金额，等于所有明细小计之和 |
| status | nvarchar(20) | 否 | 排队中 | 排队中／制作中／待取餐／已完成／已取消 | 当前业务状态 |

订单不保存员工外键，当时的值班员工通过 DutyRoster 计算。退款保留订单、明细和原始成交金额，统计销售额时按业务口径筛选状态。排队阶段退款取消后保存“已取消”状态；仍保留成交金额和原料消耗快照，用于避免重复恢复库存。

### 3.9 OrderItem 订单明细

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| item_id | varchar(10) | 否 | — | PK | 当前手工分配的明细编号，如 T001 |
| order_id | varchar(10) | 否 | — | FK → SalesOrder.order_id | 所属订单 |
| product_id | varchar(10) | 否 | — | FK → Product.product_id | 商品 |
| product_name_snapshot | nvarchar(50) | 否 | — | 非空白 | 购买时商品名称 |
| quantity | int | 否 | 1 | > 0 | 同配置的购买杯数 |
| base_price_snapshot | decimal(10,2) | 否 | — | >= 0 | 购买时不含加料的每杯价格 |
| unit_price | decimal(10,2) | 否 | — | >= 0 | 含所选规格加价和加料的成交每杯价格 |
| sub_amount | decimal(10,2) | 否 | 计算列 | unit_price × quantity，显式转换为 decimal(10,2) | 明细小计，PERSISTED NOT NULL 计算列 |

unit_price = base_price_snapshot + 本明细全部规格 price_delta_snapshot 之和 + 全部加料 price_snapshot 之和。总金额已经包含规格加价和加料，统计订单金额时不能再次累加这些费用。sub_amount 定义为 `sub_amount AS CAST(unit_price * quantity AS decimal(10,2)) PERSISTED NOT NULL`，INSERT 时省略此列；数据库保存计算结果，修改数量或单价后自动重算，不能直接写入或更新小计。超出字段容量的订单必须拒绝，不能截断。此计算列只负责明细小计，不会自动更新 SalesOrder.total_amount，也不负责汇总规格及加料价格。

### 3.10 ItemSpec 明细规格选择

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| item_id | varchar(10) | 否 | — | 联合 PK，FK → OrderItem.item_id | 明细 |
| spec_type | nvarchar(20) | 否 | — | 联合 PK，温度／糖度／杯型 | 选择类型 |
| spec_id | varchar(10) | 否 | — | 与 spec_type 联合 FK → Specification(spec_id, spec_type) | 选择的规格 |
| spec_name_snapshot | nvarchar(20) | 否 | — | 非空白 | 购买时规格名称 |
| price_delta_snapshot | decimal(10,2) | 否 | — | 不设置非负 CHECK | 此商品选择该规格时的每杯加价快照 |

主键 (item_id, spec_type) 保证每条明细每种类型最多一个选项，例如不能同时选“五分糖”和“无糖”，也不能同时选“中杯”和“大杯”；复合外键保证选择记录的类型与规格定义一致。

已确认 ItemSpec 表示该明细实际选择的规格：同一商品在不同明细中可以具有不同选择。ProductSpecification 表示商品允许哪些规格及其当前加价，两表职责不同。下单时应核对该明细商品存在可用的 ProductSpecification 配置，并从配置复制 price_delta_snapshot；此规则涉及跨表，需由操作流程验证。

移除单个 factor_snapshot 字段，因为一个所选规格可能有多个原料系数。退款继续依据 OrderItemIngredient 保存的实际扣减量，无需从修改后的规格规则重算。若将来要求逐条追溯当时的系数，再另行设计原料级规则快照；当前不额外增加该表。

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |

### 3.13 DutyRoster 值班表

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| duty_id | varchar(10) | 否 | — | PK | 当前手工分配的单名员工值班记录编号，如 D001 |

### 3.14 SpecificationIngredient 商品规格原料系数表

| 字段 | SQL Server 类型 | 空 | 默认值 | 域与约束 | 含义 |
|---|---|---|---|---|---|
| product_id | varchar(10) | 否 | — | 联合 PK，与 spec_id 联合 FK → ProductSpecification(product_id, spec_id) | 具体商品 |
| spec_id | varchar(10) | 否 | — | 联合 PK，与 product_id 联合 FK → ProductSpecification(product_id, spec_id) | 此商品的具体规格选项 |
| ingredient_id | varchar(10) | 否 | — | 联合 PK，FK → Ingredient.ingredient_id | 被调整的原料 |
| factor | decimal(5,2) | 否 | — | >= 0，具体范围按业务规则确定 | 该规格选项对这一种原料基础用量的系数 |

联合主键 (product_id, spec_id, ingredient_id) 保证同一商品同一选项对同一种原料只有一条规则。一个商品规格配置可以对应多个 ingredient_id，各原料可以有不同 factor；同一选项在不同商品上也可以有不同 factor。系数 0 表示不使用该种基础原料，1 表示不改变，大于 1 表示增加用量。对已完成定义的商品规格配置，没有规则行的基础原料按系数 1 处理；未完成定义的配置应停用，不能以“没有行”作为可销售依据。

多种已选规格对同一种原料均有规则时，按已确认方案乘积叠加：先按商品取得基础用量，再乘该商品各选项对此原料的系数。计件耗材不能产生非整数用量，杯子不能随饮料体积系数放大。规则必须针对该商品基础配方中已有的原料，纯系数不能增加配方中原本不存在的原料。

## 5 计算与验证口径

对一条明细和一种原料：

基础部分按已确认的多原料规则表和系数乘积计算。加料按每杯每种最多一份，将所选加料的 extra_amount 与基础部分相加，再乘以明细杯数；当前简化版本不对加料应用规格系数。不能把尚未完成定义的规格或未确定的系数当作 1 自动下单。

```text
基础部分 = 基础配方用量 × 所有已选规格对此原料的系数乘积
           （配方、规格配置和系数规则均按本条明细的 product_id 查询）
           （已完成定义但没有此原料规则的选项系数为 1，没有基础配方行时基础部分为 0）
加料部分 = 所有选中且对应此原料的加料每杯用量之和
明细原料消耗 = (基础部分 + 加料部分) × quantity
```

计算原料用量时统一四舍五入到两位小数，再保存消耗快照并执行扣减；检查、扣减和退款必须使用相同精度。计件原料禁止通过舍入掩盖非整数用量，应直接拒绝该配置。整笔订单需要先按原料汇总所有明细的消耗，再检查库存，不能逐杯独立检查后认为整单库存足够。

样例预期结果：

- O001 金额 = 9 × 1 + 6 × 2 = 21 元，购买 3 杯。
- O002 金额 = (8 + 1) × 1 = 9 元；无糖、去冰没有糖浆及冰块扣减行。
- O003 金额 = (6 + 1) × 1 = 7 元。
- 三个订单全部原料扣减汇总：柠檬 150g、糖浆 90ml、茶汤 1000ml、牛奶 200ml、珍珠 150g、芋圆 50g、冰块 300g、椰果 40g、杯子 5 个。
- 若从付款前库存演示，应以 Ingredient 样例库存加上上述扣减汇总作为初始库存；若直接装载当前快照，则不能再扣一次。
- 若 O002 退款，只恢复茶汤 200ml、牛奶 100ml、珍珠 50g、椰果 40g、杯子 1 个；同一订单不能重复退款。
- “已完成销售额”样例为 21 元，销量 3 杯；“未退款已付款金额”样例为 37 元，两种口径应分别命名。
- 商品销量汇总应从 OrderItem 按订单状态筛选后聚合，不直接连接规格、加料、消耗表后求和，避免一对多连接使金额和数量重复累计。
- 值班团队查询每个订单可返回多行员工；不能在此结果上直接汇总订单金额，否则多人值班会重复累计同一订单。销售统计和员工归属展示应分别聚合。

按订单时间查询值班团队的后续 SQL 口径：

```sql
SELECT o.order_id, o.order_time, d.duty_id, e.employee_id, e.name
FROM dbo.SalesOrder AS o
LEFT JOIN dbo.DutyRoster AS d
    ON o.order_time >= d.start_time
   AND o.order_time < d.end_time
LEFT JOIN dbo.Employee AS e
    ON d.employee_id = e.employee_id;
```

使用 LEFT JOIN 保留缺少值班记录的订单，便于发现值班数据遗漏；这些订单不能据此判定没有员工参与。上述区间匹配口径已用于 query.sql 和 crud_demo.sql，并在本机 SQL Server 的回滚验证中检查了交接前后团队及未匹配排班的情况。

## 6 数据库约束与流程验证的分工

单表 CHECK、主外键、UNIQUE 和 NOT NULL 可以保证字段域、引用存在、选择不重复、库存非负，以及值班结束时间晚于开始时间。

下列规则涉及跨表或前后状态，不能仅用普通 CHECK 宣称已实现；第三周先写操作脚本，第四周补充正反例，后续阶段按课程要求演进为过程或事务：

| 规则 | 后续实现与证据要求 |
|---|---|
| 订单必须有明细、总额等于明细之和 | 创建整单后核对；失败不得留下半张订单 |
| 成交单价等于基础价快照、规格加价快照及加料价快照之和 | 下单时统一计算；跨表核对查询应返回零条异常 |
| 只能购买在售商品、可用原料和加料 | 下单操作检查状态，并测试下架商品、缺货原料及加料购买失败 |
| 所选规格必须适用于商品 | 检查 ProductSpecification 中存在对应商品、规格的可用配置，类型通过现有规格复合外键核对 |
| 一个选项调整多种原料、多个选项影响同一种原料 | 从 SpecificationIngredient 按商品、所选规格、原料取规则并乘积叠加；验证同商品同选项同原料重复规则被联合主键拒绝、系数 0 及大于 1 的计算结果 |
| 系数只调整该商品基础配方中已有的原料 | 检查规则原料在对应 Recipe 中存在；不通过规格规则执行原料添加或替换 |
| 一次付款完成订单、明细、选择、消耗快照与库存扣减 | 作为一次完整业务操作；原子性和并发实验留到课程对应阶段 |
| 退款只能从排队中发生且只能恢复一次库存 | 检查原状态并保存已取消；测试制作中及重复退款失败 |
| 状态按指定路径推进，不能完成后重新制作 | 更新操作检查原状态；CHECK 只能限制状态枚举 |
| 会员积分只在首次完成时增加 | 完成操作检查原状态；非会员、退款、重复完成不能增加积分 |
| 原料单位与用量一致，计件数量为整数 | 验证引用单位与数值；禁止修改已经使用的原料单位 |
| 名称、价格及用量快照反映购买时数据 | 创建时写入并限制后续修改；修改当前商品或配方后核对历史记录 |
| 同一员工的值班区间不能重叠 | 联合 UNIQUE 只能拦截同一开始时间；另需检查任意两段是否交叠，跨员工交叠合法 |
| 订单按创建时间匹配所有值班员工 | 测试多人同时值班、班次交接时刻、跨日及缺失值班记录；历史查询保留离职员工 |

已有建表脚本不代表上述跨表流程规则已在数据库中生效；仍须提供操作脚本及正反例执行结果。
