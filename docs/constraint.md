# 第四周：constraint.sql 约束设计要求

本文件记录已确认的完整性设计，并同步独立 `constraint.sql` 的实现与验证状态。第 1—8 节为设计要求，第 9 节为当前复现与验证说明。角色权限与受控操作见 [role.md](role.md)。

## 1. 文件职责

`constraint.sql` 应独立于建表脚本保存，负责创建或补充数据库完整性约束，并包含合法数据成功、非法数据被拒绝的验证用例。

现有约束保留，缺失约束补齐，避免重复定义。约束必须在数据库中实际生效，不能仅在报告中描述。安装时核验已有数据，不以禁用检查的方式绕过错误。

验证使用测试数据，结束后回滚测试记录；已经安装的约束保留。文件应支持重复执行。

## 2. 主键和唯一性

### 2.1 独立实体编号

员工、值班、会员、商品、规格、原料、加料、订单及订单明细使用各自的编号作为主键。

编号必须非空、非空白，且不能重复。名称不默认唯一：不同员工可以同名，不同商品也可能同名。

### 2.2 联系表的联合主键

| 表 | 联合主键 | 保证的规则 |
|---|---|---|
| Recipe 基础配方 | 商品编号＋原料编号 | 一个商品对一种原料只定义一条基础用量 |
| ProductSpecification 商品规格配置 | 商品编号＋规格编号 | 一个商品对一个选项只定义一条配置 |
| SpecificationIngredient 规格原料规则 | 商品编号＋规格编号＋原料编号 | 同一商品、同一选项、同一原料只有一个系数 |
| ItemSpec 明细规格选择 | 明细编号＋规格类型 | 同一明细同类型最多选择一个选项 |
| ItemAddOn 明细加料选择 | 明细编号＋加料编号 | 同一明细不能重复选择同一种加料 |
| OrderItemIngredient 原料消耗快照 | 明细编号＋原料编号 | 同一明细对同一种原料保存一条合并后的消耗量 |

联合主键负责防止重复记录；外键负责保证引用对象或组合存在，两者职责不同。

### 2.3 其他唯一性要求

| 对象 | 唯一性要求 |
|---|---|
| 会员 | 手机号不能重复 |
| 规格 | 同一规格类型下的名称不能重复 |
| 值班 | 同一员工不能有两条开始时间完全相同的值班记录 |
| 规格编号与类型 | 组合可供明细规格的复合外键引用，保证编号和类型匹配 |

同员工开始时间唯一并不等于值班区间不重叠；任意时间区间交叠还需要维护操作检查。

## 3. 外键和引用规则

| 引用表 | 引用关系 | 业务含义 |
|---|---|---|
| DutyRoster | 员工编号 → Employee | 值班记录必须属于已有员工 |
| SalesOrder | 会员编号 → Member | 会员订单必须引用已有会员；游客订单的会员编号为空 |
| OrderItem | 订单编号 → SalesOrder；商品编号 → Product | 明细必须属于已有订单并引用已有商品 |
| Recipe | 商品编号 → Product；原料编号 → Ingredient | 配方两端对象必须存在 |
| ProductSpecification | 商品编号 → Product；规格编号 → Specification | 商品可选规格必须引用已有商品和选项 |
| SpecificationIngredient | 商品＋规格 → ProductSpecification | 商品必须配置了这个规格 |
| SpecificationIngredient | 原料编号 → Ingredient | 被调整的原料必须存在 |
| SpecificationIngredient | 商品＋原料 → Recipe | 被调整的原料必须属于该商品的基础配方 |
| AddOn | 原料编号 → Ingredient | 每种加料对应一种已有原料 |
| ItemSpec | 明细编号 → OrderItem；规格编号＋类型 → Specification | 所选规格必须存在，且编号与类型一致 |
| ItemAddOn | 明细编号 → OrderItem；加料编号 → AddOn | 选择记录必须引用已有明细和加料 |
| OrderItemIngredient | 明细编号 → OrderItem；原料编号 → Ingredient | 消耗快照必须引用已有明细和原料 |

### 3.1 本轮确认的配方复合外键

在原有规格原料规则外键的基础上，增加“商品编号＋原料编号引用配方表”的复合外键，保留原有外键。

两个复合外键分别检查：

- 商品＋规格：这个商品是否配置了这个选项。
- 商品＋原料：这个商品的配方是否包含这个原料。

例如柠檬水配置了大杯且配方包含柠檬，则“大杯调整柠檬”合法。牛奶虽然存在于原料表，但不在柠檬水配方中，“柠檬水大杯调整牛奶”必须被拒绝。

新增外键不改变库存存放位置，也不自动修改库存。修改配方用量、规格系数不受该引用关系限制；删除或更换被规格规则引用的配方原料前，必须先处理对应规则。

## 4. 字段域、非空和默认值

### 4.1 数值要求

| 字段或数值 | 合法范围 |
|---|---|
| 商品基础价格、订单总金额、明细基础价快照、成交单价、加料价格及价格快照 | 大于或等于 0，允许免费商品或零金额 |
| 商品规格差价、明细规格差价快照 | 不设置必须非负的限制；最终成交单价仍必须非负 |
| 原料库存、会员积分、员工月薪 | 大于或等于 0 |
| 购买杯数 | 大于 0 的整数 |
| 基础配方用量、每份加料用量、原料消耗快照 | 大于 0 |
| 规格原料系数 | 大于或等于 0；0 表示取消该基础原料，1 表示不变，大于 1 表示增加 |

金额与原料用量沿用两位小数，系数沿用两位小数。库存与用量的单位由原料表定义。

以“个”为单位的原料，库存、基础配方、每份加料及每杯调整后的用量都必须是整数。不能通过多买几杯或四舍五入掩盖每杯 1.5 个的错误配置。

库存整数检查可以由库存行内 CHECK 完成；配方、加料、规格调整及快照是否计件，涉及引用原料单位，需要相应维护和下单操作检查。

`role.sql` 的规格启用操作除单项检查外，还检查每种可用规格类型各选一项的全部组合；两类型、三类型系数乘积产生非整数计件用量时拒绝启用并回滚。本规则属于受控操作，不增加普通 CHECK。

### 4.2 枚举和格式

| 字段 | 允许值或格式 |
|---|---|
| 员工在职状态 | 在职、离职 |
| 员工业务岗位 | 店员、店长；这个字段不等于数据库角色 |
| 商品状态 | 在售、下架 |
| 原料状态、加料状态 | 可用、缺货 |
| 商品规格配置状态 | 可用、停用 |
| 规格类型 | 温度、糖度、杯型 |
| 订单状态 | 排队中、制作中、待取餐、已完成、已取消 |
| 原料单位 | g、ml、个 |
| 会员手机号 | 11 位数字，首位为 1；只作课程项目格式检查 |
| 值班时间 | 开始时间严格早于结束时间 |

### 4.3 非空与默认值

必填的编号、名称、数量、价格、用量、状态及引用字段不能为 NULL；编号与必填名称不能只包含空格。

| 字段 | 默认值 |
|---|---|
| 员工状态 | 在职 |
| 会员积分 | 0 |
| 商品状态 | 下架 |
| 原料库存 | 0 |
| 原料状态、加料状态 | 可用 |
| 商品规格配置状态 | 停用，规则完成后再启用 |
| 商品规格差价 | 0 |
| 明细购买杯数 | 1 |
| 正式订单状态 | 排队中 |
| 正式订单创建时间 | 当前门店时间 |

商品描述可以为空。订单的会员编号和游客编号分别允许为空，但它们之间必须遵守下一节的互斥要求。

## 5. 会员与游客订单归属

不新增顾客业务资料表。订单使用以下两个字段记录购买身份：

| 字段 | 类型 | 含义 |
|---|---|---|
| member_id | varchar(10)，允许 NULL | 会员订单的归属，引用会员表 |
| guest_id | uniqueidentifier，允许 NULL | 非会员顾客会话的临时 ID |

两者必须且只能填写一个：

- 会员订单：member_id 非空，guest_id 为空。
- 游客订单：member_id 为空，guest_id 非空。
- 同时为空或同时非空：拒绝。

游客 ID 由系统生成并绑定当前顾客会话。同一次访问的多笔订单共用这个 ID，刷新页面应保留它。因此不能把 guest_id 定义成订单表中的唯一字段，也不能每插入一笔订单就自动生成一个新的会话 ID。

订单中的临时 ID 不随会话结束清除，仍作为历史归属记录保存。身份字段的正确格式和互斥只属于完整性检查；“当前调用者是否有权使用这个身份”属于角色和受控操作的检查，不能仅凭知道一个 ID 就允许查询或退款。

如果已有非会员历史数据缺少归属，实施前需要明确兼容处理方式。仅凭 member_id 为空，无法推断哪些旧订单属于同一次顾客会话；不能把任意生成的占位 ID 宣称为已认证的原顾客身份。

## 6. 金额和消耗快照

每杯成交单价等于商品基础价格快照、所选规格差价快照及所选加料价格快照之和。明细小计等于成交单价乘购买杯数，采用计算列，不能直接手工修改。订单总金额等于全部明细小计之和。

规格系数只调整基础配方中的已有原料。同种原料受到多个已选规格影响时，系数相乘。独立加料按每杯固定一份计算，不应用规格系数；同一种原料来自配方和加料时，先合并再保存消耗快照。

付款成功时保存实际成交名称、价格及最终原料消耗快照。后续修改商品价格、名称、配方和规格规则，不得重算或改写历史成交数据。退款使用原始消耗快照返库。

## 7. 普通约束与受控操作的分工

| 规则 | 数据库约束能保证的部分 | 受控操作还必须保证的部分 |
|---|---|---|
| 订单状态 | 状态值属于规定枚举 | 按排队中 → 制作中 → 待取餐 → 已完成推进，不能跳步或回退 |
| 订单规格 | 引用存在，类型匹配，同类型最多一项 | 每种开放类型必须一项；默认选项也保存；必须适用于商品且可用 |
| 订单金额 | 数值非负，明细小计自动计算 | 根据成交配置计算单价，整单汇总一致，订单至少一条明细 |
| 库存 | 库存非负，计件库存为整数 | 汇总整单需求后检查、扣减；创建订单和扣库一起成功或一起失败 |
| 退款 | 已取消是合法状态值 | 仅排队中可退款，取消与返库同一事务，不能重复返库 |
| 积分 | 积分为非负整数 | 首次完成才按整单金额向下取整加分，退款和重复完成不加分 |
| 值班 | 员工存在，结束晚于开始，相同开始时间不重复 | 同员工任意两段值班不能重叠；不同员工可同时值班 |
| 原料单位 | 单位属于规定枚举 | 已使用原料不能直接换单位，跨表计件用量必须整数 |
| 订单归属 | 会员与游客字段必须二择一，会员引用存在 | 身份取自可信绑定，查询和退款核对本人归属 |
| 历史保留 | 外键保护已有引用，不采用级联删除历史记录 | 业务角色不能物理删除核心资料和订单，也不能修改历史快照 |

## 8. 约束验证要求

每个用例必须说明准备数据、执行操作、预期结果与实际拒绝原因。合法数据成功和非法数据失败都应有可执行证据。

| 用例 | 预期结果 |
|---|---|
| 插入不同编号的合法商品 | 成功 |
| 再插入同一商品编号 | 主键拒绝 |
| 两个会员使用相同手机号 | 唯一约束拒绝 |
| 明细引用不存在的订单或商品 | 外键拒绝 |
| 商品规格规则引用配方外的已有原料 | 配方复合外键拒绝 |
| 商品原料正确，但商品没有该规格配置 | 商品规格复合外键拒绝 |
| 库存为 -1，或杯数为 0 | CHECK 拒绝 |
| “个”原料库存为 1.5；ml 原料库存为 1.5 | 前者拒绝，后者允许 |
| 基础价格为 0、系数为 0 或大于 1 | 允许 |
| 规格差价为负，但最终成交单价非负 | 允许 |
| 必填名称为 NULL 或全空格 | 非空或非空白检查拒绝 |
| 订单状态写为“配送中” | 枚举检查拒绝 |
| 值班结束不晚于开始 | 时间检查拒绝 |
| 会员与游客身份同时为空或同时填写 | 归属互斥检查拒绝 |
| 同一游客会话下两笔订单共用一个 ID | 允许 |
| 删除被规格规则引用的配方原料 | 外键拒绝 |
| 省略具有默认值的字段 | 写入规定默认值 |
| 直接修改明细小计 | 拒绝；修改数量或单价后小计自动重算 |

对预期失败，不能把任意 SQL 错误都视为通过。需要确认确实是目标约束拒绝，而不是字段拼写、表不存在等无关错误。

## 9. 当前实现与复现说明

管理员先执行现行 `db_creation.sql` 和 `seed_data.sql`，再在无未结束事务的新窗口完整执行 `constraint.sql`；业务角色和受控操作随后由 `role.sql` 安装。建库脚本会删除并重建 TeabarDB，仅用于首次初始化或明确需要重置的场景。约束脚本支持重复执行，不重建数据库。

安装部分在事务中保留已有约束并补齐缺失的键、字段域、非空与默认值，添加 SalesOrder.guest_id、归属互斥、计件库存整数、值班及明细编号非空白检查，并添加规格规则引用基础配方的复合外键。全部 FK/CHECK 使用 WITH CHECK 重新核验并启用；旧数据违反约束时安装回滚。缺少归属的旧非会员订单逐单生成占位 ID，只作兼容处理，不代表认证或原会话还原。

2026-10-06 独立 SQL Server 测试库中 44/44 个正反例通过，重复执行通过；反例核对错误号和目标约束或字段名称，验证记录最终回滚，安装好的约束保留。`role.sql` 的 84 个角色及业务验证用例也通过，其中包含新增的计件规格组合校验。两文件共同覆盖完整性与受控业务流程；仅运行约束文件不能证明身份隔离、状态流转、退款返库或积分结算已经生效。本次验证未升级现有 TeabarDB。
