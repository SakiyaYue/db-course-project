## 二、v0.1 冻结策略

不建议把“给当前 Git 提交打标签”和“开始修改数据库”混为一件事。应分成两层冻结。

### 2.1 Git 源码快照

当前仓库处于干净的 `main` 分支，第一阶段成果已经提交，因此当前提交适合作为第一阶段源码快照。

建议：

1. 在当前提交上创建不可移动的 `v0.1` 标签，表示“第一阶段提交时的原始状态”。
2. 不在打标签前混入第二阶段代码或大规模整理。
3. 打标签后再建立第二阶段开发分支，例如 `codex/phase-2` 或小组约定的分支。
4. 如果后来只修正第一阶段文档，可以另记为 `v0.1.1`，不要移动已经发布的 `v0.1` 标签。

这样可以保证以后始终能够回答：迁移前的原始代码到底是什么。

### 2.2 数据库迁移基线

数据库基线不能只靠 Git 标签确认。正式编写 `migration.sql` 前，需要先在独立数据库副本中复现和登记。

建议先完成以下工作：

- 按现有 README 在新的测试数据库环境中完整执行第一阶段脚本；
- 确认脚本执行顺序和对象安装结果；
- 记录表、字段、主外键、视图、过程和数据库角色；
- 保存迁移前关键查询结果；
- 保存关键表行数和必要的校验值；
- 记录约束 44 项和角色 84 项验证结果；
- 保留数据库备份或可恢复副本；
- 明确该数据库副本为 `v0.1` 迁移源；
- 后续只在该副本的复制品上试跑迁移。

因此推荐顺序是：

```text
立即保存当前 Git 源码快照
→ 只读复现并登记数据库基线
→ 整理第 5 周设计材料
→ 确定 v1.0 目标结构
→ 编写和试跑 migration.sql
```

不要直接在当前正在使用的 `TeabarDB` 上试跑迁移，也不要用 `db_creation.sql` 删除重建数据库来代替迁移。
