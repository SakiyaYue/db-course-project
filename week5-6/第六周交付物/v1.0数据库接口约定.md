更新日期：2026-11-09。状态：**已部署到独立工作库TeabarDB_Phase2_Work，SQL层184项回归通过；真实受限连接和 Web 联调属于后续应用阶段。** [实测结果](迁移前后结果与已知限制.md)、[迁移脚本](SQL脚本/README.md)及[目标模式](v1.0目标模式与对象变更.md)可供接入。既有参数与结果以冻结 [role.sql](../../role.sql) 为准。

## 1. 通用调用规则

所有普通输入由 DAO 占位符绑定。认证接口在受限应用入口身份调用，业务接口在已验证的 `web_*` 身份下调用；服务端取得身份，不向下单过程传会员/游客编号、单价、总额或客户端角色。

表名、视图名、过程名是固定接口常量；身份切换使用固定允许名单模板。每次请求校验会话版本，关闭连接池，先处理事务再 REVERT/关闭连接。事务范围、保存点和错误处理遵循现有核心过程，不在 JSON 包装中复制扣库/写单逻辑。

初版外部订单与明细 ID 采用 10 位大写 ASCII：前缀 `O`/`I` 加 9 位随机大写十六进制字符，由 B 使用安全随机源生成；数据库 PK 最终保证唯一。碰撞时整个操作失败，确认无写入后重新生成整组 ID，最多重试 3 次；只把已识别的订单/明细主键碰撞作为重试条件。该格式用于新 Web 编号，不限制 v0.1 既有编号。

## 2. 新增 JSON 下单入口

### 2.1 签名与结果

`teabar_api.usp_PlacePaidOrderJson`：

| 参数 | SQL 类型 | 约定 |
| --- | --- | --- |
| `@order_id` | `NVARCHAR(MAX)` | 先宽参数接收；仅接受非空、无首尾空白、1—10 位 ASCII 字母/数字/下划线/短横线，再转换成原 `VARCHAR(10)` |
| `@items_json` | `NVARCHAR(MAX)` | 非空 JSON 数组，至少一项；元素为 `{item_id, product_id, quantity}` |
| `@specs_json` | `NVARCHAR(MAX)` | JSON 数组；元素为 `{item_id, spec_id}`；每种配置类型必须选一项，由核心业务过程判定 |
| `@addons_json` | `NVARCHAR(MAX)` | JSON 数组；元素为 `{item_id, addon_id}`；无加料传 `[]` |
| `@payment_succeeded` | `BIT` | 1 模拟付款成功；0/NULL 不创建正式订单 |

宽订单参数是对 D04 草案类型的细化，避免 SQL 在进入过程前将超长字符串截断，导致过程无法识别原始输入。核心 TVP 过程仍沿用 `@order_id VARCHAR(10)`；B 也必须先做长度与格式校验。

成功返回一个结果集、一行：`order_id VARCHAR(10)`、`total_amount DECIMAL(10,2)`、`status NVARCHAR(20)`，初始状态为排队中。不新增业务成功 JSON 层；DAO 转成应用响应。失败由 THROW 报错，不返回伪成功行。

```json
{
  "order_id": "O123ABC456",
  "items": [{"item_id": "I123ABC456", "product_id": "P001", "quantity": 2}],
  "specs": [{"item_id": "I123ABC456", "spec_id": "S001"}],
  "addons": [],
  "payment_succeeded": true
}
```

这是结构示例；成交条件由实际菜单和规格选择决定。DAO 将三个数组分别序列化绑定，不把整个 HTTP 对象直接传给 SQL。

### 2.2 严格校验顺序

1. 检查三个参数非 NULL、为合法 JSON 数组；数组中的每项必须是对象，items 非空。兼容级别要求至少 130，不为了支持 JSON 擅自降低或提高现库兼容级别。
2. 使用 `OPENJSON` 默认模式先枚举对象属性与类型：字段集合精确、属性名区分大小写、不重复、不缺失、不接受额外的价格/身份等字段。不能直接以窄类型 WITH 投影替代原始类型、长度检查。
3. ID 必须为 JSON 字符串，满足与订单号相同的 1—10 位 ASCII 规则；quantity 必须为 JSON 数字，原始词法为正整数字面量、INT 范围内，不接受字符串、布尔、小数或科学记数法。先检查再转换，禁止截断或舍入通过。
4. 检查 items 的 item_id 唯一、specs 的 `(item_id,spec_id)` 唯一、addons 的 `(item_id,addon_id)` 唯一；选择必须引用本次 items。不得悄悄去重、忽略无效行或补默认规格。
5. 装载原三个 TVP，调用唯一核心下单过程。规格适用性、同类型重复、计价、购买身份、逐明细消耗、库存与事务由核心检查；SQL 仅解析参数，不将 JSON 拼为动态 SQL。

属性键的大小写/重复检查显式采用二进制比较，业务 ID 的重复检查按目标数据库排序规则，避免校验与 PK 比较语义不同。原始字符串使用实际长度检查，不能让 LEN 忽略尾部空白掩盖超长输入。

### 2.3 错误号分配

静态扫描现有 SQL 后预留以下号段；实现前再次确认未被其他新增脚本占用。现有业务错误号原样传递，不包装成统一的数据库错误号。

| 号码 | 条件 | 应用处理 |
| --- | --- | --- |
| `52018` | 某条明细没有正消耗，整单拒绝 | 配置/业务失败；失败明细编号记录在服务端日志 |
| `52600` | NULL、非法 JSON、非数组或 items 空 | 参数错误 |
| `52601` | 元素非对象、字段缺失/重复/多余、属性大小写不符 | 参数错误 |
| `52602` | ID 类型/格式/长度不符，或 quantity 类型/词法/范围不符 | 参数错误 |
| `52603` | 重复明细或重复选择 | 参数错误 |
| `52604` | 规格/加料引用不属于本次订单的明细 | 参数错误 |
| `52700` | Web 会话/账号/映射/授权状态无效 | 终止该请求，要求重新登录或拒绝访问；具体原因只记后端 |

`52015` 保留为原整单零需求检查。本次核心先执行逐明细检查，因此非空订单中单条或全部零消耗优先抛 `52018`；这是有意新增的非法输入拒绝行为，原合法流程与现有 84 项覆盖行为应保持。

常用原错误号：`52000` 购买身份/权限不符，`52001` 模拟付款失败，`52005` 商品不可售，`52007` 非法或停用规格，`52008` 同类型重复，`52009` 漏选规格，`52016` 库存不足/缺货，`52103` 非法状态流转，`52105` 退款他人订单，`52106` 非排队或重复退款。唯一冲突 `2601/2627`、FK/CHECK `547` 和权限 `229` 需按上下文转成友好应用错误，不能把数据库堆栈发到浏览器。

## 3. 新增认证接口

### 3.1 `teabar_auth.usp_GetWebCredential`

参数：`@login_name NVARCHAR(MAX)`。先拒绝超长、空白、格式不符输入，再与唯一登录名匹配；用户名限 3—50 位小写 ASCII 字母、数字、点、下划线或短横线，B 输入层可转小写，但数据库存储使用统一小写格式。

返回列：`account_id INT`、`password_hash NVARCHAR(512)`、`session_version INT`。匹配且启用时最多一行；无匹配或禁用返回零行。带盐哈希只在可信后端用配套库校验，不由 SQL 用明文比对，也不发往浏览器。未找到账号时 B 使用固定虚拟哈希执行一次校验，外部仍返回统一登录失败。

角色与 SID 在验密成功后通过上下文接口取得；凭据查询不建立会话、不修改积分或业务数据，也不直接承担密码错误计数策略。

### 3.2 `teabar_auth.usp_GetWebContext`

参数：`@account_id INT`、`@session_version INT`；任何无效状态抛 `52700`，不返回可用映射。

成功列：`account_id INT`、`app_role VARCHAR(10)`、`principal_sid VARBINARY(85)`、`principal_name SYSNAME`、`session_version INT`。会员/游客编号不作为调用下单的参数返回，由数据库业务身份函数自行取得。

检查账号存在且启用、版本一致、SID 对应恰好一个允许名单中的无登录 SQL 用户、唯一业务角色匹配、没有额外直接角色成员关系；customer/member 还需活动且类型匹配的 PrincipalBinding，并核对绑定保存的 principal_name 与系统目录。需要对系统目录名称比较统一排序规则。工作角色不要求购买绑定。

仅 `teabar_web_app` 获得两个认证过程 EXECUTE，并获得检查所需六个用户和四个角色的最小逐对象元数据可见权限；不得授全库 VIEW DEFINITION 或通过 OWNER 上下文扩大业务身份。授权有效性和元数据可见性必须在真正受限连接下验证。

密码重置、账号停用、角色或 SID 更换均由管理员初始化/维护脚本负责，同时递增版本；应用业务角色没有账号表写权限。本轮不新增自助注册接口。

## 5. 原写入接口与交接验证

`usp_AdvanceOrder(@order_id VARCHAR(10), @next_status NVARCHAR(20))` 返回 `order_id,status`，仅店员/店长合法推进；`usp_RefundOrder(@order_id VARCHAR(10))` 返回 `order_id,status`，购买者仅能退本人排队订单，店员/店长可按原范围协助。

`usp_AdjustStock(@ingredient_id VARCHAR(10), @operation NVARCHAR(10), @amount DECIMAL(10,2))` 返回 `ingredient_id,stock,unit`，operation 为补库或盘点；仅店长。`usp_FindMember(@phone VARCHAR(20))` 返回 `member_id,name,phone,points`，仅原授权工作角色。

其余 `usp_SaveMember`、`usp_SaveProduct`、`usp_SaveIngredient`、`usp_SaveEmployee`、`usp_SaveSpecification`、`usp_SaveProductSpecification`、`usp_SaveRecipe`、`usp_SaveSpecificationIngredient`、`usp_SaveAddOn`、`usp_SaveDutyRoster` 沿用原类型、可空/默认参数和角色授权，不新增结果集；B 通过对应查询确认保存结果。完整声明见冻结 `role.sql`，本轮没有更改这些签名。

A/B 后续验证：参数化普通查询/写入；JSON 正常、多商品及格式反例；单条/混合零消耗；库存不足无部分写入；完成积分与退款返库；购买者互相隔离；店员/店长越权；账号禁用或版本变更使旧会话失败；异常 REVERT/释放连接；应用入口及业务用户不能读账号表、随意切换用户或直接写业务表。

## 6. SQL 行为依据

订单参数先宽接收再检查，依据是 SQL Server 对过程参数及变量赋值的截断行为，见 Microsoft [SET ANSI_WARNINGS](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-ansi-warnings-transact-sql?view=sql-server-ver17)。JSON 默认模式的属性/类型枚举与兼容级别要求见 [OPENJSON](https://learn.microsoft.com/en-us/sql/t-sql/functions/openjson-transact-sql?view=sql-server-ver17)。数据库身份切换与作用域见 [EXECUTE AS](https://learn.microsoft.com/en-us/sql/t-sql/statements/execute-as-transact-sql?view=sql-server-ver17)。驱动、权限和异常路径仍需实测。
