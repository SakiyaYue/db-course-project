依据：[共同决策 D01—D05](../../PHASE2-DECISIONS.md)、[函数依赖与范式分析](函数依赖与范式分析.md)、[有意冗余说明](有意冗余与业务状态说明.md)。本文细化已对齐方向，不增加采购、多仓、真实支付、自助注册或员工账号自动授权业务。

## 1. 目标关系模式

### 1.1 保留现有 16 表

完整关系属性、字段类型和约束见 [v1.0 数据字典](v1.0数据字典.md)。本轮目标不拆表、不合表、不重命名、不废弃旧表或旧接口：

| 分组 | 保留的关系 | 处理理由 |
| --- | --- | --- |
| 交易 | `SalesOrder`、`OrderItem`、`ItemSpec`、`ItemAddOn`、`OrderItemIngredient` | 保留归属、金额、名称/价格/消耗快照和历史标识 |
| 商品配置 | `Product`、`Specification`、`ProductSpecification`、`Recipe`、`SpecificationIngredient`、`AddOn` | 保留当前商品、规格、配方和加料的独立事实与关联码 |
| 资源与人员 | `Ingredient`、`Member`、`Employee`、`DutyRoster` | 保留单门店库存、积分、业务岗位和多人值班 |
| 身份 | `teabar_auth.PrincipalBinding` | 保留当前数据库 SID 到购买身份的映射；会员编号不增加唯一约束 |

`OrderItem.sub_amount` 继续使用现有持久化计算列；包含该列的关系存在已解释的 3NF 例外。`ItemSpec` 保留 3NF、非 BCNF 结构，以主码和复合 FK 直接保证规格类型规则。

### 1.2 新增 `teabar_auth.WebAccount`

```text
WebAccount(
  account_id INT IDENTITY(1,1),             -- PK
  login_name NVARCHAR(50),                 -- NOT NULL, UNIQUE
  password_hash NVARCHAR(512),             -- NOT NULL
  app_role VARCHAR(10),                    -- customer/member/clerk/manager
  principal_sid VARBINARY(85),             -- NOT NULL, UNIQUE
  is_active BIT DEFAULT 1,                 -- NOT NULL
  session_version INT DEFAULT 1            -- NOT NULL, > 0
)
```

候选码为 `account_id`、`login_name`、`principal_sid`，各自决定其余属性；没有其他非码决定因素，按本轮业务规则满足 BCNF。`app_role` 表示此账号应当拥有的角色，不能反推唯一账号。角色与数据库角色成员关系之间的一致性属于跨对象安全规则，由管理员初始化与认证上下文接口共同检查。

每账号映射一个独立 `web_* WITHOUT LOGIN` 数据库用户，SID 在账号表唯一；不重复保存数据库用户名，也不在本表重复保存 `member_id`、`guest_id`。数据库用户名称按 SID 从系统目录解析；购买者再经现有 `PrincipalBinding` 解析归属。店员、店长没有购买身份绑定也可拥有账号。

SID 不对 `PrincipalBinding` 建 FK，因为那会错误要求工作账号也必须具有购买身份；也不对 SQL Server 系统目录建立用户表 FK。管理员和上下文接口必须检查 SID 对应唯一、有效的指定数据库用户。重建用户后不自动继承旧账号绑定；先禁用账号、核对身份和授权，再更新映射、递增会话版本并记录操作。

`session_version` 用于停用、重置密码、改角色或改 SID 后使旧会话失效。会话只保存 `account_id` 和登录时版本等必要信息；每次业务请求重新解析有效上下文，版本不一致即要求重新登录。

## 3. 安全对象与初始化边界

### 3.1 目标角色与用户

保留四个业务角色及六个 `demo_*` 用户。首轮演示新增六个独立用户：`web_guest_a`、`web_guest_b`、`web_member_a`、`web_member_b`、`web_clerk`、`web_manager`，分别属于唯一对应的业务角色；全部使用 `WITHOUT LOGIN`，由后端在数据库连接内进行身份切换。

新增受限应用入口用户 `teabar_web_app`，映射部署时提供的连接身份。连接可由受限 SQL Login 或受限 Windows 身份提供，具体凭据与登录对象由管理员配置；禁止把开发者管理员连接当最终运行身份。入口不是上述业务角色成员。

| 入口/主体 | 明确授予 | 不授予 |
| --- | --- | --- |
| `teabar_web_app` | 两个认证过程 EXECUTE；三个公开菜单视图 SELECT；逐个 `web_*` 的 IMPERSONATE | 业务基表写入、账号/绑定表直接读写、demo/任意用户切换、用户/角色管理、db_owner |
| `web_guest_*` | `teabar_customer` 原能力及 JSON 过程 EXECUTE | 切换身份、读取认证哈希、其他人的订单 |
| `web_member_*` | `teabar_member` 原能力及 JSON 过程 EXECUTE | 任意改积分、读取其他会员数据 |
| `web_clerk` / `web_manager` | 对应原角色能力 | 认证材料、切换身份、直接修改历史快照或核心业务表 |

公开视图为 `teabar_api.vw_Menu`、`vw_AvailableSpecifications`、`vw_AvailableAddOns`。未登录请求停留在应用入口身份，只读这三项。浏览器从不直接持有数据库凭据或认证查询结果。

认证过程由 dbo 所有的 `teabar_auth` 架构提供受控静态查询，调用上下文仍为调用者；不对业务用户开放认证过程，不使用 `WITH EXECUTE AS OWNER` 执行业务下单。四类角色对账号表不授 SELECT/DML。

### 3.2 认证与请求流程

1. 登录：B 参数化调用凭据查询，在服务端用配套密码库验证带盐哈希；成功后解析上下文并建立会话。不存在、禁用或映射无效时统一返回登录失败，不向浏览器区分原因。
2. 每请求：入口身份调用上下文过程，核对账号启用、会话版本、SID、对应角色及购买身份。账号每次只允许一个业务角色，不接受客户端数据库用户名或购买身份。
3. 身份切换：DAO 只使用部署时固定的 `web_*` 允许名单生成的 `EXECUTE AS USER = '固定用户'` 模板，按已核对的 SID/名称选模板。普通业务值全部参数化；不要把身份名称当普通查询参数，或拼接客户端提供的名称。
4. 请求结束：先完成或回滚事务，再 REVERT，最终关闭连接；失败无法确认恢复的连接丢弃。首版关闭连接池，B 必须验证成功、异常、会话失效等路径。
5. 管理员初始化：先创建用户和唯一业务角色授权，再写购买者绑定和 WebAccount；密码哈希从管理员本地输入/环境传入。初始密码、哈希和应用密钥均不写进仓库或演示截图。

上下文失败必须拒绝业务执行。购买者要求活动绑定且满足：customer 使用 guest 身份、member 使用 member 身份；工作角色不要求绑定。上下文验证还检查 principal 为预期 `web_*` 的无登录数据库用户、没有额外直接角色成员关系。初始化与回归继续核验没有额外直接授权、架构所有权或高权限，不能仅凭应用角色列推断数据库权限。

应用入口可切换多个账号，可信后端本身属于安全边界；入口凭据泄露后，账号间隔离不再成立。

## 4. 无损连接、依赖保持与保留理由

### 4.1 本轮实际采用的变更

现有表均不进行关系分解或合并，旧列、PK/UK/FK 和成交快照保持，原关系可原样读取，因而不存在因拆合表产生的连接伪元组或依赖丢失。新增 WebAccount 记录新的账号事实，不把既有会员或员工主档迁入账号表。

账号经唯一 SID 对应数据库用户；购买者再经 PrincipalBinding 主码取得最多一个绑定。工作账号的绑定为可选关系，应使用受控分支或外连接，不可用内连接把无绑定的店员/店长账号丢弃。这个可选关联不是所有账号都必须匹配的 FK。

### 4.2 未采用的 BCNF 分解

`ItemSpec` 以 `spec_id → spec_type` 分成类型映射和选择快照时，交集 `spec_id` 决定类型映射，分解无损；但是“一明细一类型”不再能由单表 PK 直接保证，关键依赖不保持。现目标保留 3NF 原结构及复合外键。完整推导见[分析 3.3](函数依赖与范式分析.md)。

`OrderItem` 排除派生小计后保留全部基础事实，可用同一乘法公式重建小计，不丢失可独立维护的业务事实。当前选择仍保留计算列来统一金额表达，不增加乘法结果业务表；明确保留完整关系的范式例外。

### 4.3 新账号表的异常控制

三个单属性候选码各自决定全部账号属性，满足 BCNF。新建账号需要同时准备数据库用户，是安全配置的合理前置条件；密码只更新一条账号记录。修改角色/SID/启用或密码时递增会话版本，管理员同步更新授权与绑定；删除账号不删除订单，演示账号优先停用。系统目录与账号映射的跨对象一致性不由单表范式保证。
