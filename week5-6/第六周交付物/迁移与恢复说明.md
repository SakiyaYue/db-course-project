# v0.1 到 v1.0 迁移与恢复说明

更新日期：2026-11-09。本人已在 SSMS 中完成副本创建、默认演练、故障回滚、正式提交及 184 项回归；过程见[实操记录](实操.docx)，结果见[迁移前后结果](迁移前后结果与已知限制.md)。

## 1. 运行前提

| 项目 | 要求 |
| --- | --- |
| 冻结源库 | TeabarDB，完整 v0.1；16 表、74 列、19 条外键 |
| 工作副本 | TeabarDB_Phase2_Work，初始为完整 v0.1 |
| 样例基准 | 15 张业务表共 232 行，PrincipalBinding 另 4 行 |
| 目标 | 17 表、81 列、19 条外键；WebAccount 初始为空 |
| 身份 | 复制操作使用有备份/还原权限的管理员；迁移及回归在库内为 dbo |
| 会话 | 每阶段使用无外层事务的窗口，工作库无应用并发写入 |

本次截图显示实例为 localhost、SQL Server 17.0.1000。首次建立完整 v0.1 使用第一阶段已验证的初始化顺序；迁移从现有源库复制，保留其数据和对象。

## 2. 创建工作副本

1. 打开 [work-copy.sql](SQL脚本/数据库迁移脚本/work-copy.sql)。默认 `Execute=0`，源库为 TeabarDB，工作库为 TeabarDB_Phase2_Work。
2. 完整执行以查看计划，核对输出的备份、数据和日志路径。目录是 SQL Server 服务端目录，须存在且服务身份可写。
3. 将 `Execute` 改成 `1`，完整执行。脚本按顺序 COPY_ONLY + CHECKSUM 备份、VERIFYONLY 校验、MOVE 还原到新文件。
4. 出现 `WORK_COPY_RESTORED_KEEP_BACKUP` 后，保存备份路径，在对象资源管理器刷新 Databases。

模板支持一数据文件和一日志文件，不覆盖已有工作库。根目录 `db_creation.sql` 会删除、重建 TeabarDB，不能用于重置迁移副本。

## 3. 确认上下文与迁移前结构

在 SSMS 新建查询窗口，数据库选择 TeabarDB_Phase2_Work：

```sql
SELECT DB_NAME() AS database_name,
       USER_NAME() AS database_user,
       @@TRANCOUNT AS transaction_count;

SELECT
    (SELECT COUNT(*) FROM sys.tables WHERE is_ms_shipped=0) AS tables,
    (SELECT COUNT(*) FROM sys.columns c JOIN sys.tables t
     ON t.object_id=c.object_id WHERE t.is_ms_shipped=0) AS columns,
    (SELECT COUNT(*) FROM sys.foreign_keys) AS foreign_keys;
```

预期为工作库、dbo、事务数 0，以及 16 / 74 / 19。需要保留详细业务基准时，可在此时运行 [business-query-compare.sql](SQL脚本/数据库测试脚本/business-query-compare.sql) 并保存结果。

## 4. 默认演练、故障回滚与正式提交

打开 [migration.sql](SQL脚本/数据库迁移脚本/migration.sql)，搜索两个开关声明，每次修改后完整执行同一文件。文件已内嵌全部模块，无需生成步骤。

| 顺序 | CommitMigration | InjectFailure | 预期与后续 |
| --- | --- | --- | --- |
| 1 默认演练 | 0 | 0 | 执行并检查目标结构后回滚，输出 DRY_RUN_ROLLED_BACK_TO_V0.1 |
| 2 回滚核验 | — | — | 执行 verify-rollback.sql，输出 ROLLBACK_OBJECT_CHECK_PASSED |
| 3 故障演练 | 0 | 1 | 目标 DDL 完成后主动报 52809，输出 MIGRATION_FAILED_ROLLED_BACK |
| 4 再次核验 | — | — | 再执行 verify-rollback.sql，检查原对象和基准数据恢复 |
| 5 正式提交 | 1 | 0 | 目标检查通过后提交，输出 COMMITTED_V1.0 |

回滚核验入口为 [verify-rollback.sql](SQL脚本/数据库测试脚本/verify-rollback.sql)。其表哈希应与同次迁移的 `PRE_MIGRATION` 对应表一致。`VALIDATED_BEFORE_COMMIT` 是事务内、最终提交或回滚之前的检查结果；回滚后的结构与旧过程另由核验脚本检查。

故障演练预期为错误 52809，其他错误应先调查原因。故障结果应显示 `transaction_state=0`、`transaction_count=0`、`webaccount_after_rollback=NULL`、`original_core_restored=1`。结果过多时向下查看结果集，并查看 Messages 标签。

## 5. 提交后的验证

1. 运行 [v1.0-object-capture.sql](SQL脚本/数据库测试脚本/v1.0-object-capture.sql)，检查 WebAccount 的 7 个字段、主键及登录名/SID 唯一约束、新增 3 个索引、3 个过程；FK/CHECK 的 is_disabled、is_not_trusted 应均为 0。
2. 完整执行 [regression.sql](SQL脚本/数据库测试脚本/regression.sql)。最终应输出 `REGRESSION_PASSED_TEST_DATA_ROLLED_BACK`、passed_cases=184，各组 failed=0。
3. 运行 [key-query-compare.sql](SQL脚本/数据库测试脚本/key-query-compare.sql)，应输出 `KEY_QUERY_COMPARE_PASSED`、matched_measures=10。
4. 可再次运行 [business-query-compare.sql](SQL脚本/数据库测试脚本/business-query-compare.sql)，导出订单明细、逐商品销量及全部库存，与迁移前记录对照。

regression 中的回滚只撤销测试数据和临时安全配置，工作库仍保持 v1.0。52 个新增用例在测试事务中回滚，禁止身份切换的一例在事务外隔离执行并清理；脚本随后核对 17 表及安全对象的前后哈希。

对象采集结果按字段展开，复合外键和多列索引会出现多行；统计外键或索引数量应按对象名去重。

## 6. 数据冲突与保留策略

迁移预检检查源表、字段、键、CHECK/FK 信任状态、模块和基准数据。历史明细缺少正消耗、订单金额不符、基准偏离、模块定义不符或目标对象同名冲突时停止执行。

原 16 表不拆分、合并或重命名，保留历史名称、价格及原料消耗快照；新增 WebAccount 记录独立账号事实，初始为空。核心下单新增错误 52018，JSON 入口调用原交易过程，其余合法业务语义沿用。

迁移在同一事务内取得应用锁和原表写锁，执行 DDL、过程更新、授权、哈希检查和版本标记；异常时整体回滚并抛出错误。冲突数据先调查来源，再恢复干净基线或制定单独修复方案。

## 7. 失败恢复与再次运行

| 情况 | 处理 |
| --- | --- |
| 默认演练、注入故障或事务内错误 | 确认事务结束，执行回滚核验并比较原表哈希，相符后重试 |
| 连接断开 | 重新连接，检查服务器恢复状态及实际对象，执行适用的核验 |
| 已提交 v1.0 | 工作库不能再作为迁移源；需要重做时从保留备份建立干净 v0.1 副本 |
| 工作库已有额外测试数据或未知对象 | 保存当前记录，准备干净副本后重新执行 |
| 工作库名称更换 | 统一修改复制、迁移、回滚核验、回归、对象采集和两类业务对照脚本的工作库名 |

提交后的恢复采用备份还原获得 v0.1；本项目没有就地逆向迁移脚本。执行完毕后将提交文件恢复为 Execute=0、CommitMigration=0、InjectFailure=0，实际执行配置保留在截图与日志中。
