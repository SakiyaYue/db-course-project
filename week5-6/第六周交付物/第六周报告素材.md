# 第六周函数依赖 规范化与迁移实验

## 1. 设计思路

本实验以第一阶段冻结的单门店茶饮数据库 v0.1 为基础，分析候选码、函数依赖、更新异常及范式，再选择保留、调整或新增对象。目标是在保留订单、价格和原料消耗历史的前提下，修复逐明细消耗校验缺口，并为后续应用准备账号与 JSON 接口。

基线完整安装后为 16 张表、74 个字段、19 条外键，15 张业务表有 232 行样例，另有 4 行购买身份绑定。迁移在 TeabarDB_Phase2_Work 副本实施，源库为 TeabarDB。

### 1.1 主要函数依赖与范式

商品主数据中，product_id 决定当前商品名称、基础价格、状态和描述。历史明细保存成交时快照，同一商品在不同交易中的名称或价格可以不同，因此 product_id 不决定历史成交单价。

`OrderItem` 的 item_id 决定整条明细，但同时存在 `(unit_price, quantity) → sub_amount`。该决定因素不是超码，小计是非主属性，所以包含计算列的完整关系不满足 3NF，最高为 2NF。保留基础事实投影时，已列依赖下满足 BCNF；物理实现保留数据库计算列以统一金额计算。

`ItemSpec` 有候选码 `(item_id, spec_type)` 和约束推导候选码 `(item_id, spec_id)`，同时有 `spec_id → spec_type`。右端是主属性，因此满足 3NF；决定因素 spec_id 不是超码，因此不满足 BCNF。

基线 16 表中，14 表在已分析的依赖下满足 BCNF。新增 WebAccount 的 account_id、login_name、principal_sid 各是单属性候选码，分别决定其余属性，满足 BCNF。逐表推导见[函数依赖与范式分析](函数依赖与范式分析.md)。

### 1.2 更新异常及冗余取舍

当前商品、会员、原料等主档独立保存，订单通过外键引用，因此录入主档不依赖先有订单，修改主档也无需批量重写交易。存在历史引用时由外键限制删除，商品下架、配置停用用于生命周期管理。

名称、价格及消耗快照保存成交事实；当前主档变动后快照保持原值。库存和积分是业务状态，订单总额是跨表汇总，由受控过程和事务维护。`sub_amount` 由数据库计算，业务角色没有直接重写交易快照的权限。

如果将 ItemSpec 分为 R1(spec_id, spec_type) 与 R2(item_id, spec_id, spec_name_snapshot, price_delta_snapshot)，交集 spec_id 决定 R1，因此分解无损；但“一明细一类型至多一个选项”的依赖不能由两个投影依赖单独保证。实验保留原 3NF 设计和复合外键，维持这一直接约束。

### 1.3 实施方案

原 16 表不拆分、合并或重命名，主外键和历史数据保留。新增 WebAccount 的 7 列及主键、登录名/SID 唯一约束，新增 3 个索引、JSON 下单过程和 2 个认证过程。核心下单增加逐明细正消耗检查，任一明细不合规时以 52018 拒绝整单。

因此本次迁移没有历史数据搬表任务；原表全行哈希用于检查内容是否保持。完整结构见[目标模式](v1.0目标模式与对象变更.md)、[数据字典](v1.0数据字典.md)和[ER 图](<v1.0 ER图及可编辑文件/README.md>)。

### 2.1 建立副本与基线

### 2.2 默认迁移演练

将 CommitMigration、InjectFailure 均设为 0。脚本记录 PRE_MIGRATION，事务内完成结构修改并输出 VALIDATED_BEFORE_COMMIT，最后主动回滚，结果为 DRY_RUN_ROLLED_BACK_TO_V0.1。图 3 展示事务内原数据哈希一致及回滚完成标志。

### 2.3 故障演练与恢复

将开关设为 0、1，在目标 DDL 完成后主动触发 52809。结果为 MIGRATION_FAILED_ROLLED_BACK，事务状态与计数为 0，新账号表对象为 NULL，旧核心恢复标记为 1。随后执行 verify-rollback.sql，输出 ROLLBACK_OBJECT_CHECK_PASSED，图 4—5 展示故障及恢复核验。

### 2.4 正式提交及对象检查

### 2.5 回归与关键查询对照

完整执行 regression.sql，包含 44 项原约束、84 项原角色业务、53 项新增功能及 3 项整体检查。图 8—10 展示合法与非法操作，图 11 显示各组失败数 0、最终通过数 184，并展示测试前后数据及安全配置哈希对照。

反例包括单条或混单零消耗、库存不足、付款失败等。它们分别得到预期错误 52018、52016、52001，passed=1。测试清理仅撤销测试影响，已提交的 v1.0 结构保留。

最后执行 key-query-compare.sql，10 项指标一致：4 商品、9 原料、5 订单、7 明细；P001 价格 6.00、I001 库存 5000.00、M001 积分 120；2026-10-04 已完成 3 单、5 杯、46.00 元。对应图 12，逐项对照见[迁移结果](迁移前后结果与已知限制.md)。

## 3. 实验总结

本次分析表明，规范化应依据业务依赖和全部候选码判断。历史快照、计算小计、跨表汇总和当前业务余额各有不同含义，需要分别解释与维护。保留现有结构同样需要依赖推导、异常分析和约束依据。

迁移实验验证了默认回滚、预定故障回滚和正式提交三条路径。结构新增没有改变原业务表内容；回归确认原约束、角色与交易行为保留，逐明细正消耗和 JSON 等新增检查符合预期。

现有截图保存了代表用例与总汇总。完整的订单明细、逐商品销量及全部原料库存对照入口一并提交，可进一步导出为结果附件；真实 Web 连接和页面验证继续在应用阶段完成。
